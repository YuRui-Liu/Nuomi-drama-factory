# 质量门禁：在错误扩散前退回

- **所属**：创作方法 · 07 质量门禁
- **相关技术页**：[共享系统地图](../system-map.md) · [测试策略](../development/testing-strategy.md)
- **产品入口**：[设置与任务中心](../product/07-settings-and-tasks.md) · [端到端创作管线](02-end-to-end-workflow.md)

## 适用场景

适合把创作检查变成每阶段可执行的进入、通过和退回规则，减少「上一阶段带着坏输入继续跑，最后才发现整集要重做」的情况。

## 核心观点

门禁检查的是当前阶段是否具备可消费的输入和可验证的输出，不替代审美判断。门禁结果要能指出对象、证据和下一步；不确定时退回最近的可修复阶段，并保留失败产物与任务记录。

## 判断标准

| 阶段 | 进入条件 | 通过标准 | 退回条件 |
| --- | --- | --- | --- |
| 导入 | 文件可读、格式受支持、项目身份明确 | 来源版本与剧集记录写入，导入状态可查询 | 文件损坏、路径越界、来源版本不明 |
| 拆集 | 来源文本已激活，分组规则已确定 | 集数、顺序、边界和原文引用可追溯 | 分组重叠、缺集、无法回指原文 |
| 资产 | 角色、场景、道具需求有剧本依据 | 关键资产有可读 canonical 文件或明确待生成状态 | 身份冲突、关键资产缺失、候选无来源 |
| 剧本 | 当前来源版本与语义约束一致 | Beat 可执行，角色、动作、对白、时长和必须表现内容齐全 | 事实冲突、字段缺失、时长或顺序不可执行 |
| 分镜 | ShotPlan 有镜头目的和资产引用 | 草图/首帧构图、景别、动作方向可审阅 | 主体不可辨、镜头目的不明、连续性断裂 |
| 声音视频 | 画面候选、台词文本和声音来源已锁定 | 文件可播放，时长、speaker、动作和音轨策略匹配 | provider 失败、时长不符、声音来源 stale |
| 合成 | 通过的画面、音频、字幕输入齐全 | FFmpeg 输出可播放，字幕、音轨、时长和导出包可核验 | 缺素材、时间线断裂、编码或导出检查失败 |

## 推荐工作流

1. 阶段开始前记录输入 revision、文件路径和任务状态。
2. 按表逐项检查，失败项写证据，不用「看起来不对」作为唯一结论。
3. 只把通过的对象交给下游；部分失败要标明范围，不把缺失项默认为成功。
4. 退回后重新检查受影响阶段及其直接下游；使用[测试策略](../development/testing-strategy.md)补充契约验证。
5. 合成前再做一次全链路抽查，确认使用的是当前 canonical 文件或明确选中的候选。

## 正反例

正例：视频通过前核对 MP4 可播放、实际时长、分辨率、音轨来源和 manifest；发现外部 TTS 缺 ambience stem，就退回声音/视频阶段。

反例：看到文件存在就把阶段标成完成，跳过哈希、时长和来源检查，直到合成时才发现画面仍是旧版本。

## 常见失败

- 把「任务完成」等同于「产物通过」，没有读取质量报告或实际媒体属性。
- 退回条件写成主观评价，执行者无法判断要补什么证据。
- 只重试 provider，不修复输入 revision、资产引用或连续性问题。
- 通过后修改上游文件，却没有让下游状态变为 stale。

## 软件入口

- 项目阶段与产物状态从项目生产页查看，实现入口为 `frontend/src/routes/_app/projects.$project/production.lazy.tsx`。
- 长任务、失败原因和重试从任务中心进入，实现入口为 `frontend/src/routes/_app/projects.$project/tasks.tsx`。
- 各阶段具体实现见[小说导入](../pipelines/01-ingest.md)、[剧集图谱](../pipelines/02-episode-graph.md)、[生产资产](../pipelines/03-production-assets.md)、[剧本与语义](../pipelines/04-screenplay.md)、[分镜与图像](../pipelines/05-storyboard.md)、[声音与音频](../pipelines/06-audio.md)、[视频生成](../pipelines/07-video.md)和[合成与导出](../pipelines/08-compose-export.md)。

## 检查清单

- [ ] 已记录本阶段输入的 revision、路径、来源和任务状态。
- [ ] 每个通过项都有可复核证据（字段、文件、日志或媒体探测结果）。
- [ ] 失败项已标明退回阶段和最小修复动作。
- [ ] 部分失败没有被默认为整体成功，影响范围已写清。
- [ ] 上游变更后已重新检查直接下游的 stale 状态。
