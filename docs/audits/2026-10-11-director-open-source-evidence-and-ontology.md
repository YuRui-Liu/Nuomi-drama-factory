# 分镜系统 P0–P2：开源依据、Ontology 与可验证方案

研究日期：2026-10-11。状态：设计讨论，尚未实现或通过生产验证。

本文衔接 [当前提示词与链路审计](2026-10-11-director-shot-prompts-analysis.md)。旧文保留实际提示词与代码快照；本文区分外部项目的已证实机制、针对本项目的设计推导以及尚需验证的假设。用户所说的 onpology 暂按 Ontology（本体建模）理解。

## 1. 研究结论与证据边界

建议将系统改为“模型提出导演方案，结构化事实和规则检查可执行性，人工与评测判断表达质量”。不能只向提示词追加“请合理拆镜”。

本次没有找到并验证一个能作为行业标准、直接替代导演判断的自动剧本拆镜算法。以下项目值得参考的是各自成熟领域的机制，不代表组合后已经证明能拍出好影片。星数只是采用度线索，不是导演质量证书。

| 参考 | 本次 GitHub 页面显示约数 | 已核对内容 | 对应改进 | 不应作出的推论 |
| --- | ---: | --- | --- | --- |
| [Storyboarder](https://github.com/wonderunit/storyboarder) | 3.9k | 画板模型含独立 UID、newShot、时长和音频字段 | P0-1：区分画板和镜头；先做可播放预演 | 它不是自动剧本拆镜算法 |
| [OpenTimelineIO](https://github.com/AcademySoftwareFoundation/OpenTimelineIO) | 2.0k | ASWF 项目，时间线、片段、媒体引用分层 | P0-1/P0-3：导演镜头与生成素材、剪辑时间分开 | 它不会判断叙事节奏或自动保证素材足够 |

## 2. P0-1：先分清四种对象，再讨论拆多少镜

### 2.1 外部项目具体给了什么依据

Storyboarder 的 board.js 将画板 UID、newShot 和 duration 分开保存；boardDurationWithAudio 取画板时长和音频时长的较大值。它给出的启发是：画板不是仅凭序号等同于独立镜头，音频也会约束预演时间。[源码](https://raw.githubusercontent.com/wonderunit/storyboarder/master/src/js/models/board.js)

OTIO 将 Clip 与媒体引用、使用区间分开，并以 Track/Stack 表达时间线组合。文档明确指出，某些媒体越界情形仍需下游处理。因此应借鉴对象边界，同时自行实现生产可行性检查。[时间线结构](https://opentimelineio.readthedocs.io/en/latest/tutorials/otio-timeline-structure.html)

### 2.2 本项目建议的领域区分

| 对象 | 回答的问题 | 示例 |
| --- | --- | --- |
| Beat 叙事节拍 | 观众在此知道了什么、情势怎样变化 | 莉娅发现孩子没有影子 |
| Shot 连续镜头 | 用哪一段连续视听观察表达信息 | 从莉娅视线摇到车厢地板，无剪切 |
| Board 分镜图 | 镜头内哪个瞬间需要视觉设计 | 地板亮、孩子脚边没有影子的瞬间 |
| Generation segment 生成片段 | 当前服务实际生成什么素材 | 一段提供首帧的素材，供剪辑选用 |

一个 Beat 可由多个 Shot 覆盖；一个 Shot 可有多个 Board；生成素材与最终剪辑镜头的映射应显式记录。第一阶段仍可保留现有受支持的单镜头生成路径，但不能把该实现限制伪装成普遍电影规则。生产提交单位仍是叙事组，不另造逐镜绕过流程。

### 2.3 拆镜不能等同于按句子、动作数、秒数切块

建议先建立“必须传达的信息清单”，再生成可选观察方式。对每个候选边界记录原因：新信息揭示、主观视点变化、时空跳转、反应强调、动作衔接，或不需要切镜。模型负责提出方案，程序检查声明是否自洽。

当前 s2 把递面包、看车厢、孩子无影、切回莉娅、车夫劝签塞进一个 shot。真正可证实的问题是文本明确声明了内部剪切，数据却没有相应镜头边界。不能由此断言所有这类段落必须固定拆成四镜。

可供导演评估的方案：

| 候选 | 表达方式 | 优点 | 代价与待验证点 |
| --- | --- | --- | --- |
| A | 接面包与邀请 → 车厢无影揭示 → 莉娅反应与车夫遮挡 | 揭示顺序清楚，关键帧容易覆盖 | 镜头数增加；对白和总时长仍需重新预算 |
| B | 连续跟随莉娅靠近，镜头下摇揭示脚边，再回到两人关系 | 保留动作和空间连续性 | 遮挡、运镜距离、人物保持能力要求更高 |
| C | 一个生成片段包含多个显式镜头 | 可能减少生成任务数 | 必须有分镜级时间和参考图映射；现链路不应默认支持 |

推荐先让 A、B 都能被规范表达；先执行现有适配器可支持的方案，C 后置。不能为了迁就 4–15 秒约束，把两秒插镜强制延长成四秒，或者把所有动作无理由切碎。

### 2.4 可确定检查与仍需判断的部分

- 程序可检查：Shot ID 唯一、信息项均有覆盖、跨镜过渡有对象、Board 归属明确、生成映射完整。
- 语义审核可发现：一个声明连续的镜头，说明却要求独立反打或瞬移视角。必须返回原句和冲突字段。
- 人工/视觉评测判断：这个反打是否必要、悬念是否过早泄露、长镜是否更有力量。

出现“切”字只能触发线索，不能直接判错。例如人物切面包、镜头结尾切黑均不是镜头内非法剪切。

## 3. P0-2：可以借 Ontology，但要建制作事实模型

### 3.1 为什么这比补一段资产目录更稳

Palantir 的官方介绍同时强调对象、属性、关系以及产生变更的动作。这里借的是这种建模方式；不需要采购 Foundry，也不需要立即引入 RDF、OWL 或图数据库。[官方说明](https://www.palantir.com/docs/foundry/ontology/overview)

建议先用现有数据库与 Pydantic 保存显式关系。LinkML 可作为领域模型描述的参考，但现阶段没有必要增加第二套 Schema 真源。[LinkML](https://github.com/linkml/linkml)

### 3.2 必须拆开的实体

| 类型 | 含义 | 不能混淆为 |
| --- | --- | --- |
| Character | 故事中的人物 | 一张头像 |
| Appearance | 特定服装、年龄、身份造型 | 所有同名人物 |
| Asset | 可用于制作的资源记录 | 已可访问的媒体文件 |
| MediaVersion | 实际图片/音频及其版本与状态 | 资产名称 |
| Location | 稳定空间实体 | 从街道到侧门的一整段运动描述 |
| Event | 原文发生的事件及前后状态 | 没有证据的模型补写 |
| Requirement | 某镜头为了表达信息需要的引用 | 所有出场名词都必须有专用图 |

示意关系：Character → hasAppearance → Appearance → representedBy → Asset → hasVersion → MediaVersion。Shot 通过 Requirement 引用适用造型和媒体版本；Event 通过 source_span 指回原文。

### 3.3 用本次缺失案例检验

**“王后薇拉”与“薇拉”**：优先查稳定 ID 和已批准别名。唯一命中才能自动绑定；如果有两个时期造型，不能仅凭相似名字随便选。输出至少区分 entity_not_resolved、appearance_ambiguous、asset_not_linked、media_not_ready、media_unreachable。

**“马车中的三个孩子”**：可能是集合角色、三个已有角色，或尚无设计的背景群体。不得凭空发明三个人名，也不能因为单人资产没有同名记录就认定剧本非法。应保存 count=3 的群体要求及是否需要独立设计，由镜头重要性决定是否阻断。

**“雪城石板街·皇家慈善马车旁至钟楼侧门”**：它可能组合了主场景、道具位置和运动路径，不一定是一个新场景资产名。解析为已有 Location + 相对位置 + route 候选后，再检查是否有原文及资产关系支持；不能把一切带“石板街”的名字强行设为同义词。

### 3.4 状态与证据同样重要

每条自动推断关系保存 source、source_span、confidence、approval_state；每次制作保存使用的资产和造型版本。别名新增属于受约束操作，应有作用域和变更记录。

故事内状态与制作状态分开：契约从完整变为烧毁，是事件状态；契约参考图加载失败，是媒体状态。缺图片不能让模型把烧契约情节删掉，也不能用文本说“图片存在”绕过实际文件检查。

必需引用不足时，应显示具体对象、失败层级和可执行修复入口。若已有资产但绑定错误，应修复绑定；若确实缺少必需设计，应补设计；若只是非关键背景且允许文本表达，应明确降级策略。三个结论不能都叫 missing_asset。

### 3.5 成本和边界

收益是减少同名误配、引用漂移和跨镜状态矛盾。成本是旧记录迁移、别名审核、版本关联与服务端解析规则。Ontology 不会自动决定哪个镜头好看，也不会凭空解决实体识别；低置信度候选仍需保留歧义。

首期只建本集涉及的对象与关系，向导演提供相关子集及可查询目录。不要把整个项目的所有资产全文塞进每次提示词。

## 4. P0-3：从“填写秒数”改为时间约束

### 4.1 借鉴的机制

OR-Tools 的 Job Shop 示例把任务时长、前后依赖及资源不能同时占用的条件显式化。它适合说明约束如何被计算，而不是证明电影动作必须遵循工业调度最短工期。[Google 官方示例](https://developers.google.com/optimization/scheduling/job_shop)

本项目先实现简单依赖图的时间检查即可。只有未来存在大量替代方案、并行资源和组合选择时，才考虑 CP-SAT；无需为了引用高星项目立即引入求解器。

### 4.2 时间来源分三种

1. 实测：已有对白音频的实际时长、素材实际帧数。
2. 经样本校准的估计：某语言与表演速度下的对白区间、文字可读时间。
3. 导演假设：一个犹豫或转身大约需要多久，必须标注不确定性。

不要写一个统一“每秒四个字”就宣布校验客观。对白语速、停顿和情绪不同；既有音频可利用，不默认新增付费 TTS/ASR。

### 4.3 计算示例，仅为规则演示

假设五个事件：读出契约关键信息 2 秒 → 莉娅质问 2 秒 → 车夫完整回答 3 秒 → 拉向车灯并点燃 4 秒 → 影子显现并被看见 2 秒。若导演声明它们必须依次完成，下界为 13 秒。再加 2 秒不可重叠的反应停顿，下界为 15 秒。

这些数字不是对当前视频的实测，不是电影通用规则。它说明：如果模型同时声明 14 秒总长和上述严格依赖，程序可以指出具体矛盾；若部分动作可以重叠，则应改变依赖，不能简单累加。

计算方式：最早开始时间等于所有前置事件最早结束时间的最大值；结束时间等于开始加时长。估计区间应传播为区间并标明假设。只对确实互斥的动作或资源禁止重叠，不能禁止人物一边走一边说话。

### 4.4 三类检查结果

| 类别 | 例子 | 处理 |
| --- | --- | --- |
| 硬冲突 | 有环依赖、时间越界、已知音频长于承载区间、供应商不支持该长度 | 阻止提交，返回冲突项 |
| 高风险估计 | 多段完整对白与复杂动作挤入短时长，但没有实测音频 | 提醒并要求说明/调整，不能装作精确物理定律 |
| 艺术选择 | 为紧张感停留、故意省略过渡动作 | 由导演判断，记录理由 |

总时长也需明确是硬目标还是约数。保持 90 秒、完整对白、所有事件和所有镜头最短长度可能无解。系统应报告冲突集合，提出调速、重新分配、改覆盖或修改目标的选项，不能暗中删剧情或无条件拉长整集。

## 5. P1-1：统一核心合同，保留不同阶段的职责

Pydantic 的判别联合类型可用显式 kind 选择结构，避免多个可选字段组合出不清楚的状态。[官方说明](https://pydantic.dev/docs/validation/latest/concepts/unions/)

建议统一 Shot、Board、EntityRef、Timing、Transition 等核心类型及版本。初稿、修复和审核读取同一核心合同；修复可以多带 issue_responses，审核可以返回 issues，不应强迫三个响应外壳完全相同。

推荐校验次序：

1. 结构：字段、类型、枚举、额外字段政策。
2. 引用：ID 存在、造型适配、媒体可用、版本一致。
3. 叙事覆盖：必需事件与对白都有承载；跨镜重复引用原文允许，但不得把同一句对白播放两次。
4. 时间与连续性：已声明依赖可满足，状态衔接可解释。
5. 执行映射：所选模型、模式、参考图和生成片段一致。
6. 创作审核：揭示顺序、构图、节奏是否有效。

Pydantic 不能单独证明数据库中存在某资产，更不能证明“孩子无影”的画面让观众看懂。引用解析和创作审核必须保持为独立检查。

初稿缺必需字段时，不应靠修复阶段较严格的 Schema 偶然补齐。服务端激活前执行完整检查；前端和 CLI 共用服务端结果，返回同样的 issue_code、对象路径、原文依据、建议动作。

迁移时为旧版本提供显式转换和 unresolved 状态；不能对缺失字段填假值并宣称旧任务已经通过新标准。

## 6. P2：评测先行，提示词去重和局部修复随后

promptfoo 支持 JSON 检查及 JavaScript/Python 自定义断言，也支持模型评分。这里应优先使用确定性检查，艺术评分单独展示。[断言文档](https://www.promptfoo.dev/docs/configuration/expected-outputs/)

### 6.1 建议建立的固定案例集

| 案例 | 要验证什么 | 不应奖励的行为 |
| --- | --- | --- |
| 当前 s2 隐藏切镜 | 连续 shot 与剪切声明一致 | 删除无影揭示来通过 |
| 当前 s3a 时间密集 | 依赖、对白及动作预算有依据 | 只把 14 改成 15 |
| 合理长镜 | 连续观察方案可以通过 | 强制所有镜头最多一个动作 |
| 短插镜 | 剪辑长度与生成素材长度分开 | 一律拉成供应商最短时长 |
| 薇拉别名 | 唯一映射可复用已有资产 | 相似名自动合并所有人物 |
| 三个孩子 | 群体要求数量与身份不被篡改 | 编造三个人物身份 |
| 石板街至侧门 | 场景、位置、路径分开 | 创造不存在的场景资产 |
| 资产有记录但文件不可达 | 正确分类媒体错误 | 只检查名称就放行 |
| 原文一行覆盖多镜 | 覆盖完整、对白不重复 | 为唯一引用规则删除镜头 |
| 切黑与切面包 | 语义区分合法描述 | 关键词触发误杀 |
| 模型切换 | 重新检查派生视频模式 | UI 选项改了而执行计划未改 |
| 局部修复 | 未受影响的已批准内容保持 | 为修一镜重写全片 |

开发集和留出集分开，同一模型版本、输入资产快照、能力配置及相同试验条件对比旧提示词与新提示词。重复运行记录波动；若服务无法固定随机性，明确说明，不虚称完全可复现。

指标分别报告：硬约束通过率、故事覆盖率、错误资产绑定数、误阻断数、修复次数、未受影响字段漂移、token/耗时，以及盲评的视听表达质量。不合并成一个可被平均值掩盖的总分。模型裁判必须给证据且与硬约束分开；小样本通过不能宣传为生产成功率。

### 6.2 提示词去重如何验证不退化

将规则集中为四块：任务目标、核心对象定义、事实与能力输入、输出合同及审核标准。同一资产/时长规则只保留一个权威定义。程序负责拼装版本化合同，作者与审核引用相同标准。

先证明精简版在固定样本中不增加遗漏，再考虑 token 优化。提示词越短不是目标，跨阶段含义一致才是目标。

### 6.3 局部修复按依赖扩大

起点是失败对象，修复范围应包含会被影响的相邻镜头、人物状态、时长和参考绑定。只改措辞可以限于一镜；拆镜会影响 Board 和视频映射；改造型会影响使用该造型的后续镜头。

修复输出带 base_revision 与 changed_ids；应用前检查版本冲突，应用后重验受影响范围及全局覆盖/总时长。旧生成结果保留历史并标记适用版本，不能悄悄当成新版成果。

## 8. 建议落地顺序与验收边界

1. 先固定真实失败和正例，建立基线。此处将 P2 的评测部分提前。
2. 明确 P0-1 对象定义，同时落实 P1-1 核心合同，避免只改提示词。
3. 落实 P0-2 实体、造型、资产和媒体解析，前端呈现具体错误层级。
4. 落实 P0-3 已知时间冲突检查和估计风险提示。
5. 再精简提示词与做依赖范围修复，用留出案例验证。
6. 在同一叙事组服务入口验证网页、CLI 和 Skill，最终以真实素材与播放确认表达，不能只凭 JSON 合法宣告整集完成。

建议验收要求：固定回归中已知硬错误均被定位，合法长镜和短插镜不误杀，现有资产不因显示名称不同丢失，同一方案在网页/CLI 得到一致结果。真实视听效果须另行验证；本文未运行模型对比、未支付生成费用、未声称这些建议已有效提升生产成功率。
