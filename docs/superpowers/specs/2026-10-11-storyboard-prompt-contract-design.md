## 3. 统一数据与构建流程

`已采用导演方案 + 用户修订 → 静态画格合同 → 实际参考附件清单 → 提示词构建 → 参数/引用检查 → 组级生成 → 图片验收`

### 3.1 静态画格合同

每格必须有稳定 panel_id、shot_id、原文关联、选定 anchor、可见状态、单一构图、出场实体和动作归属、场景、相机、当前光线、允许出现的剧情文字。叙事目的、对白、镜头完整动作和剪辑理由保留在导演方案，不直接灌入生图正文。

一格表达一个机位的一个瞬间。需要多瞬间才能读懂的动作由导演显式设多个画格，不允许生图模型自行拼贴。画格数由方案决定，排版容量不反过来决定叙事。角色设计图的正侧背视图均代表同一个人物，不是多个演员。

开始和结束状态分开保存，机位、站位、朝向、视线、道具归属及光源也必须与该时刻对应。历史自由文本无法可靠转换时标记需补齐并展示建议差异，不用关键词删除冒充语义转换。

### 3.2 参考附件合同

每个实际附件包含 entity_id、显示名、用途（基础形象/场景/道具/构图/风格）、版本或内容哈希、适用 panel_ids、最终序号。

编号从最终实际上传的附件列表生成。筛选、去重、加入草图之后重新编号；禁止手工将 referenceOrder 当作已上传证据。缺图、身份歧义和超过模型参考容量均显示具体问题，禁止静默截断。

人物用完整基础形象 sheet；已有设计直接复用，缺失时可由画布建角色节点。场景参考中的人影不得被当作新增演员。仅附属于本组画格的必要资产，参考图本身不赋予角色出场资格。

### 3.3 构建职责

提取主线中不依赖任务队列的纯构建逻辑，供主线与画布调用。避免画布直接依赖私有 runner 函数；队列、费用和媒体调用维持各自适配。

构建产物包含最终提示词、按序附件清单、有效模型/尺寸/画幅/风格、导演与编辑版本、构建器版本、依赖哈希及可读诊断。网页预览、CLI 检查及实际提交使用同一产物，执行时再次确认版本未变。

优先级：已确认用户修订并入新合同后成为依据；选定时刻的结构化事实决定画面；参考图只约束其声明的用途；风格不改变人物身份和动作事实。相互冲突的用户编辑与合同先生成修订差异，不把两段相反指令同时发给模型。

## 4. 提示词示例：结构演示，不是已验证成品模板

```text
交付：一张按声明布局排列的分镜图。每格为一个完整、连续的相机画面。
禁止字幕、格号、气泡和画中画。剧情内文字仅按每格清单出现。

参考用途：
Reference 1 = 莉娅完整基础形象。同一短发红斗篷少女的多视图。
Reference 2 = 诺尔完整基础形象。同一银蓝长发蓝衣少女的多视图。
Reference 3 = 钟楼环境；不从环境图引入人物。
上述编号必须来自本次真实附件清单，此处仅为演示。

画格：诺尔在薄雪上画马车的选定瞬间
机位：俯视近景，注意力集中于持炭条的手与雪上图案。
可见主体：诺尔的一只蓝袖手持炭条；不要求人物全身入镜。
当前状态：马车图案已形成，炭条尖端停在最后一笔旁。
动作归属：持炭条并画图的是诺尔。莉娅不持炭条。
环境：钟楼内薄雪地面；沿用本场夜间光线。
剧情文字：此格无文字；“孩子”“名字”只在各自指定格出现。
不在此格表现后续起身、奔跑或额外特写。
```

这个例子展示从叙事动作提取静态画面的方式，不规定 G1 必须四镜、不改写原文，不把“禁止重复人物”当作身份绑定的替代品。实施时先从已采用导演方案确定各格瞬间，再输出完整 G1 请求供审查。

## 5. 导演介入与局部修复

网页与 CLI 可以编辑人物绑定、关键帧瞬间、机位、构图、可见主体和剧情文字。用户锁定字段不被重新导演覆盖。Skill 负责调用公共检查/执行入口、读取最终请求和检查产物，不再手工堆叠第二套通用提示词。

修改角色或画格时计算受影响组；保留无关组和历史图片。旧图标记过期，视频引用不得继续默认消费失败或过期图。修复前先区分绑定错误、静态画面投影错误、导演方案错误和模型未遵循；前两种先修输入，第三种提出局部导演修订，第四种才考虑受控重新生成。

## 6. 验收

### 无付费验证

1. 同一合同经网页/CLI 构建，最终提示词、附件顺序与参数一致。
2. 参考图重排、去重、加入草图时，身份编号和格位范围同步变化；丢图及超容量有明确错误。
3. 用户更改人物、构图或瞬间，最终请求和依赖哈希改变；无关后续动作变化不污染当前静态画面。
4. 样本 B 的静态请求不得含“跑到侧门、卡栓”作为开场状态；不能仅靠删掉 motion_path 达成。
5. 对白不变成字幕；明确的“孩子”“名字”作为剧情文字保留，不与全局“无文字”冲突。
6. 旧画布保留原节点和产物；未迁移合同给出具体诊断，不悄悄使用泛化模板。

### 首组真实验证

冻结相同角色设计版本、画风、模型和分辨率，记录 G1 原请求与新请求的具体差异。先人工审查最终请求及附件，再只生成 G1。验收身份区分、每格实际人数、手和道具归属、可见瞬间、剧情文字、相邻格空间关系、关键叙事信息。

任何一项明显错乱仍标记未通过。保存图片、请求、附件哈希与检查结论；仅在 G1 通过后推进其他受影响组，不自动开启反复付费质量循环。单个案例通过只能证明该案例，不宣称生成确定性。

## 7. 实施顺序与风险

顺序：固定反例和局部成功证据 → 定义静态合同与迁移诊断 → 提取共用构建组件 → 接入画布及编辑入口 → CLI/Skill 同步 → 请求对照与 G1 真机验证。

主要风险是主线也存在过程泄漏，以及旧自由文本没有可靠的静态字段。用明确合同、失败诊断和最小范围迁移处理；不通过复制长提示词、正则删词或放宽验收掩盖。PNG 写入完整性属于另外的媒体链路问题，不作为本次导演提示词修复成果。

规格自检：已明确范围、旧数据处理、编辑优先级、参考容量错误和验收边界；无占位实现承诺。本轮仅只读分析与设计文档，不新增生成请求。
