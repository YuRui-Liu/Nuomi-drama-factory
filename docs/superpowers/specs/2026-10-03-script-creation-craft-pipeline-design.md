# 剧本创作 Agent 工艺流程修复设计

日期：2026-10-03。状态：推荐方向已确认，书面规格待用户审查。

## 1. 目标与依据

用户反馈：当前软件剧本格式正确，但内容无法满足生产要求。目标是让现有创作 Agent 在人物驱动、因果、场景推进、对白和连续性方面形成可检查、可返修的创作流程。

专业来源：`/Users/liuyuxiang05/Liu/剧本创作skill/script-master/`，v3.1。重点吸收 framework、writing、doctor、dialogue，以及 writing-craft-library、lines-library、pattern-library 的相关方法。原始资料是方法设计来源，运行时不依赖该机器的绝对路径。

用户已确认采用推荐方向：分阶段创作、独立审稿、定向返修、台词整合。此前 2026-09-30 规格中的“不自动循环审稿”由本规格的有限返修流程替代；其正文事实、人工采纳、导演不得暗改剧情等约束继续适用。

第一轮内容验收暂用仓库现有《逆潮回声》第一集候选及相关设计材料。用户提供其他失败稿时可替换验收材料，不改变通用流程。当前确认不表示允许覆盖已采纳生产剧本或重生成媒体。

## 2. 现状证据

- `script_creation/generation.py` 的 bootstrap 顺序是 outline → episode_synopsis → people → scenes → props → episode_script。分集规划先于人物详细设计。
- 每个文档目前调用模型一次，随后通过非空、文档类型、禁止交付声明等校验保存。未运行独立的创作质量检查和返修。
- `prompts.py` 按文档类型加载旧创作参考，但系统提示明确不执行资料中的审查流程；增加参考文本本身不能形成多阶段执行。
- `agent_teams/adapters.py` 在自定义 skills 存在时移除默认技法。这是现有可替换方法契约，不能误当故障或通过偷偷追加默认审美破坏它。
- `agent_teams/trials.py` 的 writer 试写在基础校验后返回 passed=True；它不证明创作质量合格。
- `store.py` 会把已有实质文档的新生成结果保存为候选；当前后续阶段重新读取正式文档，未使用本轮候选。需明确版本沿用语义。

## 3. 方案选择与范围

| 方案 | 收益 | 代价与局限 |
| --- | --- | --- |
| 分阶段工艺流程（采用） | 把方法落实为实际生成、审查、修订调用，有证据、有停止条件 | 增加文本调用、阶段状态和报告呈现 |
| 仅替换写作提示词 | 改动小、响应快 | 无法确保执行审稿、返修和台词整合 |
| 完整搬入总控与评委交互 | 覆盖全部原 skill 的工作方式 | 范围大、交互重，容易把创作工具变成流程填表工具 |

本次覆盖现有创建、续写、局部改稿和编剧试写的工艺方法与质量结果。复用现有文档、候选、任务取消、版本比较和模型路由。只在现有创作进度及候选区增加阶段与问题展示。

导演画面版、图像、视频、声音生成、DOCX 导出、平台投稿及全新的编剧室产品不在本次范围。声音与动作资料仅在剧本确有对应叙事需要时提供写作参考。

## 4. 方法包与创作约束

在应用包内增加版本化的精炼工艺资源，随安装发布。维护来源清单：源文件、章节、源内容哈希、提炼版本、用途。读取失败必须报告缺失资源，不能静默成为空提示词。

按阶段选择资源：

- 架构：主题与反命题、核心欲望与恐惧、关系矛盾、世界规则与限制、终局和因果主线。
- 人物：Want/Need、行为弱点、核心关系、语言指纹、压力下的选择、信息边界；特殊优势按题材说明代价、边界、反制。
- 分集：已确定人物驱动的目标、阻力、行动、后果、观众回报与下一步期待。终集允许收束。
- 正文：目标与阻碍如何发生碰撞、人物策略如何变化、信息何时被谁得知、动作和对白怎样改变局势。
- 结构审查：因果、人物动机、冲突代价、场景必要性、情绪积累、连续性和风格。
- 台词：角色辨识度、言说目的、潜台词、信息边界、解释腔、朗读自然度和动作承载的信息。

原 skill 的固定数额（每个转折三个伏笔、每场多层冲突、固定金句或爽点数量）转为按题材判断的参考，不设机械配额。不能用强加停顿、攥拳、茶凉了等固定动作制造所谓人味。关键行为应有动机；安静余波、喜剧、直白表达和有意重复均可在具体语境中成立。

已保存简报中的语言风格为权威。缺失时允许根据题材形成明确标为建议的风格假设，并展示在运行报告中；不得伪称用户已锁定。与现有正文或用户要求存在重大冲突时进入 needs_review，保留待决定项。

现有自定义 skill 继续替换默认创作方法。固定执行协议负责分阶段、证据定位、结果校验和版本保护；题材偏好与审美来自实际选择的方法及项目简报。报告记录实际生效的方法来源和版本，避免“界面挂载、运行未使用”。

## 5. 创作数据流

新项目顺序：简报 → 故事大纲 → 人物设计 → 场景设计 → 道具设计 → 分集梗概（连续剧）→ 目标集正文。大纲包含核心人物动机，详细人物设计在分集规划前完成。单篇跳过分集梗概。

每份规划文档执行生成 → 独立审查；有证据支持的阻断问题时允许一次修订和一次复查。仍有阻断问题则暂停该运行，后续阶段不消费失败草稿。已完成的上游产物保留。

正文内部阶段：

1. 初稿：读取冻结简报、人物、规则、目标集梗概及相关前文；生成干净正文和独立的简短场景意图记录。
2. 结构审查：使用新模型调用，不接收作者自评分数。按原文定位问题，给出具体影响及修复目标，同时标出应保留的有效设计。
3. 结构返修：每轮只处理有效问题及必要关联影响，最多两轮，每轮之后重新审查。
4. 台词诊断：结构达标后逐场覆盖对白，返回问题原句、目的、建议替换及理由。无问题时跳过整合调用。
5. 台词整合：只替换有定位的台词及必要的相邻动作，保留场次、事实、人物目标和情节结果。
6. 最终复查：检查先前问题是否解决，整合是否破坏因果、信息边界或风格，并检查基本文本格式。

结构审查达标且台词诊断无阻断问题、未改变正文时，可直接采用当前正文与诊断结果作为最终检查依据；发生台词整合则必须最终复查。所有阶段独立记录，不将创作分析、评分或工作卡写入正文。

续写在相同流程中读取前文、目标集计划、人物当前状态、未回收伏笔和信息获取来源。首次不引入全剧语义检索系统；超出模型上下文预算时明确报上下文容量不足，不静默截断关键前文。

### 5.1 候选与正式稿

本轮上游新候选通过检查后，可以作为本轮下游的设计依据，但必须标为“候选计划”，不能充当已发生事实。运行保存有序上下文清单：正式 revision 或本轮 artifact ID、内容哈希、用途和状态。

后续候选记录对上游候选的依赖。已有实质文档不被自动覆盖；下游候选采纳前必须确认上游依赖已采纳为相同内容，或先解决差异并重新检查。不能让依赖未采纳人物设定的正文单独进入生产。新项目空槽可按既有逻辑保存审查通过的文档。

所有生成、复查、采纳和恢复均校验原始正式文档版本及候选哈希。任一依据变化进入 needs_rebase，旧报告显示已过期。

## 6. 模块边界与持久化

| 单元 | 职责与接口 | 依赖 |
| --- | --- | --- |
| 工艺资源加载器 | 根据文档类型、阶段、题材返回指导及来源信息 | 打包资源、冻结团队配置 |
| 创作上下文构建器 | 形成明确区分事实与计划的版本化输入 | DocumentStore、运行产物 |
| 内容生成器 | 接收阶段输入，输出正文或修订候选 | 现有 text runtime |
| 质量审阅器 | 独立调用，返回问题及原文依据 | 审查准则、候选、上下文 |
| 流程编排器 | 阶段推进、调用上限、取消、恢复和状态 | 上述单元、持久化接口 |
| 质量结果呈现 | 展示阶段、待修改原因、正文证据和候选 | 现有创作界面与 API |

新增严格模型：CraftArtifact、CraftIssue、CraftReview、CraftStageRecord。字段至少包括阶段、候选文本哈希、输入清单、方法版本、审阅范围、问题 ID、维度、严重度、正文引用位置、原因、修复目标、修复记录与结论。模型生成的“已解决”声明必须经后续审查确认。

问题证据由程序校验引用文本与位置。缺失问题可定位到完整场景范围，并说明缺失的叙事作用；跨文档矛盾必须提供双方证据。不能用伪造引用阻断生成。无效报告按模型结构化输出既有重试上限处理；重试仍无效视为审查失败。

每次模型调用完成后保存独立产物和阶段记录，再决定后续调用；使用 additive schema 存储运行工艺产物，关联 run_id/step_key/stage/attempt 与内容哈希，不把所有草稿塞进列表响应。详情接口提供报告与草稿读取。

新增运行和步骤状态 needs_review，与技术失败 failed、输入过期 needs_rebase 区分。审查状态独立使用 unreviewed / passed / needs_revision / failed。历史运行缺少审查记录时显示“未做内容审查”，不得追认通过。

## 7. 停止条件、成本和恢复

- 每份规划文档最多四次逻辑调用：生成、审查、一次修订、复查。
- 每集正文最多九次逻辑调用：初稿、结构审查、最多两次修订与对应复查、台词诊断、必要整合、必要最终复查。
- 模型传输与结构化输出重试仍受现有 runtime 上限约束，另计实际请求次数与用量；禁止嵌套无界重试。
- 有确凿事实矛盾、信息越界、主角动机断裂、关键事件无因果等问题必须返修。可讨论的风格偏好记录为建议，不强行升级为阻断问题。
- 修订达到上限仍不通过：保留草稿与最后报告，进入 needs_review，显示“需要修改”而非“创作完成”。
- needs_review 不自动重排队；用户修改要求后创建关联的新运行。人工编辑保存也不会自动继承旧质量结论。
- 技术故障进入 failed；取消进入 paused。恢复复用已保存且输入哈希一致的产物，已消耗的修订次数不归零。
- 每次调用前后检查取消；写入正式文档或候选时保留现有任务身份、输入版本和事务保护。
- 审稿与写作使用独立请求，可使用同一已配置模型，不宣称已获得独立人类或多模型评审。本次默认沿用冻结的编剧模型路由，避免引入必须配置的新模型角色。

## 8. 改稿、试写与界面

局部改稿保持用户指定范围：生成候选 → 范围内质量检查 → 必要的一次修订 → 复查。检查整集背景中的事实影响，遇到范围外依赖则报告，不擅自扩大改写。仍需修改的候选可查看但不可标为审查通过。

编剧 A/B 试写使用与正式生成相同的内容流程和冻结输入，分别保存正文、实际方法、审查结果、用量及耗时。原来的基础 validation_report 与 craft_review 分开；缺审查时内容结论为 unreviewed。不得用硬编码 passed=True 表示内容通过。

现有生成面板显示“设计人物 / 写初稿 / 检查情节 / 修改情节 / 打磨对白 / 检查成稿”等可理解进度。结果区展示正文、待修改问题、引用与理由，支持查看历史候选。内部方法哈希等放入可展开详情。任务完成只表示流程结束，内容结论单独呈现。

新质量标记不作为全库历史稿的强制迁移门禁。对本流程新生成的依赖候选，采纳与交接检查其明确依赖及当前质量状态；已保存的人工稿和历史稿继续按现有交接机制处理，清楚显示未审查状态。

## 9. 内容验收

固定《逆潮回声》第一集的可验证约束：岑禾身份线索、生死和当前位置仍未确认；岑砚对暗号的判断是人物推测；第二集查地图、申请出口的承接保留。不能把末日、妹妹或固定台词写入通用模板。

现有样例中“先撑过今晚”“先看管线”“不知道”“拿地图来”使主角完成判断与指令，但是否形成足够有代价的选择、居民是否具有独立诉求、集尾是否产生阶段回报，需要对照新稿检查。此处是验收假设，不把个人审美当作已证实缺陷。

准备冻结输入包：简报、人物与规则、目标集梗概、相关前文、必须保留项。先核实本地完整资料；缺失时只进行该片段的受限比较，明确不能证明全剧连续性，不编造原项目设定。

在相同模型与参数下生成旧流程和新流程的完整目标集候选；另将现有稿作为已知参考。保存输入哈希、方法版本、输出及实际调用记录。通过正常文本任务入口运行，使用独立验收运行，不覆盖生产稿。

内容评估逐项引用正文：人物选择及代价、因果衔接、关系变化、对白辨识与潜台词、情绪回报、集尾期待、信息边界、可表演动作。采用隐藏版本标签的人工对照阅读；模型报告提供辅助证据，不能替代用户对生产可用性的判断。

必须同时提供一段对照片段及完整单集供阅读，不能只挑选最好的一句证明改善。新稿不得引入事实硬伤，且在人物选择、冲突推进和对白三个核心维度给出具体改善证据；如未达到，报告失败并继续定位，不能以格式或单元测试通过交付“已解决”。

## 10. 工程验证与完成标准

- 确认人物先于分集规划；上游质量未通过时不会调用下游。
- 用格式完整但因果断裂、角色同声、信息越界的受控模型输出验证审查与返修路径；这些测试验证编排，不声称自动理解文学质量。
- 验证不存在问题时跳过修订，存在问题时不超限；审核服务失败不会假装通过。
- 验证原文证据定位、报告与候选哈希绑定、人工编辑后报告过期。
- 验证取消、恢复、并发版本变化、方法冻结、候选依赖及采纳顺序。
- 验证自定义 skill 的替换语义、资源缺失报错、打包后资源可读。
- 验证续写、局部改稿、A/B 试写和历史记录兼容，以及前端 needs_review 展示。
- 按现有解析器校验场次、人物、△动作、OS 与画外广播，保证成稿可继续进入制作。
- 运行相关 Python 与前端回归测试、类型检查，并记录实际结果。真实模型内容验收单独记录，不用 mock 测试替代。

完成报告分为“工程流程验证”和“样稿内容验收”两项，逐项列出证据与仍需用户判断的部分。模型不可用时保留实现及失败记录，明确真实内容验收尚未完成。
