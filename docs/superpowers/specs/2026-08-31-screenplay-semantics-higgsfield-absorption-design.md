# NuomiDrama 剧本语义链与 Higgsfield 制作方法吸收设计

**日期：** 2026-08-31  
**状态：** 已批准  
**适用分支：** current main

## 1. 背景与问题

当前系统虽然已经具备 `DirectorPlanRevision`、`ShotPlan`、`NarrativeGroupPlan`、组合出图和 RunningHub MiniMax H3 视频能力，但“已有剧本进入制作”的上游仍保留旧的逐行 Beat 语义：

```text
剧本文本 -> 按行切分 -> VisualBeat -> DirectorPlan
```

这会把标题、元数据、时长、分隔线和普通格式行错误地当成可拍摄内容，也会把剧本行、戏剧节拍和镜头错误地绑定为近似一对一关系。后续角色状态、场景连续性、首尾帧选择、提示词、失效传播和旧资产映射都会因此失真。

本设计将已有剧本改为“原文不改写、语义拆解后进入制作”，同时吸收 Higgsfield 在角色一致性、场景空间锚点、镜头意图、参考装配、候选版本和分阶段质量控制方面的优点，但不引入 Higgsfield 品牌、界面或运行时依赖。

## 2. 目标与非目标

### 2.1 目标

- 将已有剧本可靠地解析为 Scene 和 DramaticBeat，再由导演层规划 Shot 与 NarrativeGroup。
- 保留原文证据，模型不得凭空添加人物、事件或对白。
- 允许用户在导演拆解和镜头设计阶段手动拆分、合并、重排和修改。
- 将角色状态、场景状态、道具、镜头意图和参考计划作为生产级结构化对象。
- 支持按受影响范围局部失效和局部重试，不自动触发付费生成。
- 删除“一行一个 Beat”产品语义和隐藏回退。
- 保留旧媒体文件，并通过人工方式绑定到新镜头。

### 2.2 非目标

- 已有剧本导入不负责重新创作或改写剧情。
- 不把小说/大纲改编和已有剧本导入合并为同一入口。
- 不让知识图谱代替剧本语义模型。
- 不自动把旧 Beat 资产猜测为新镜头的正式采用版本。
- 不实现从导入到成片完全无确认的一键生产。
- 不依赖 Higgsfield 的 API、模型、专有命名或页面设计。

## 3. 产品入口与阶段

两类入口严格分离：

```text
导入已有剧本 -> 剧本校对 -> 导演拆解 -> 镜头设计 -> 成片合成
故事/小说改编 -> 创作剧本 -> 人工确认 -> 导演拆解 -> 镜头设计 -> 成片合成
```

四个生产阶段定义如下：

1. **剧本校对**：显示原文、规范化结果和差异；只做纠错与格式整理。
2. **导演拆解**：按 Scene 展示 DramaticBeat，并显示目标、阻碍、行动、反应、转折、结果和原文证据。
3. **镜头设计**：将 DramaticBeat 转换为一个或多个镜头，编辑叙事目的、景别、机位、构图、运镜、动作、时长和首尾可见状态。
4. **成片合成**：将连续镜头组成 1～4 镜头叙事组，执行组合出图、视频、配音、质量检查和交付。

旧的“生成脚本”和“一行一个 Beat”操作替换为：

- 解析场次
- 生成导演拆解
- 生成镜头方案
- 重新生成选中场次
- 重新生成选中节拍

产品界面中的“制作脚本”仅指包含原文证据、导演拆解和镜头方案的可生产视图，不再指逐行 Beat 数据结构。

## 4. 领域模型

唯一生产语义链为：

```text
SourceDocument
  -> ScriptRevision
  -> Scene
  -> DramaticBeat
  -> DirectorShotIntent
  -> ShotPlan
  -> NarrativeGroupPlan
  -> GenerationAttempt
  -> MediaAssetVersion
```

### 4.1 SourceDocument

保存用户导入的原始文件、文件哈希、来源类型、导入时间和原始文本。原始内容永久保留，不被模型输出覆盖。

### 4.2 ScriptRevision

保存可追溯的规范化剧本版本，包括父版本、原始来源、规范化文本、差异、创建者和创建时间。已有剧本入口不得在此阶段生成新剧情。

### 4.3 Scene

表示一个场次，至少包含：

- 稳定 ID、顺序和来源范围
- 内景/外景
- 地点和时间
- 场次标题
- 动作、对白、人物名、括注和转场等结构化块
- 场次内容哈希

标题、YAML、版权字段、时长、分隔线、孤立格式行和普通章节卡可以成为文档或场次元数据，但不能直接成为 DramaticBeat。

### 4.4 DramaticBeat

DramaticBeat 是一次完整、可识别的戏剧变化，而不是原文的一行。它可以跨多行，也可以在一个 Scene 内与其他节拍共同覆盖有叙事意义的内容。

每个 DramaticBeat 至少记录：

- 稳定 ID、顺序和所属 Scene
- 原文范围与证据片段
- 出场人物
- 目标和阻碍
- 行动和反应
- 转折和结果
- 情绪或权力关系变化
- 对白线索
- 预计时长
- 必须可见的内容
- `script_fact` 与 `director_interpretation` 的明确边界

### 4.5 DirectorShotIntent

DirectorShotIntent 先描述镜头的叙事目的，再进入视觉参数。例如揭示信息、强调压迫、捕捉反应、制造反差、建立空间或完成动作转折。它不得承担剧本改写职责。

### 4.6 ShotPlan

在现有 `ShotPlan` 基础上扩展：

- 关联 DramaticBeat 和来源范围
- 叙事目的
- 主体与动作
- 可见起始状态和结束状态
- 景别、机位、构图和运镜
- 空间锚点与视线连续性
- 对白来源
- 时长
- 所需角色、场景和道具状态

一个 DramaticBeat 可以生成一个或多个 ShotPlan，不建立机械的一对一关系。

### 4.7 NarrativeGroupPlan

按照角色状态、场景状态、光照/时间、动作、视线和连续性组织 1～4 个镜头。每个叙事组只发起一次组合出图调用。5 个以上镜头必须在导演规划阶段拆组，执行层不得静默拆分。

## 5. 解析与生成流程

### 5.1 确定性场次解析

解析器先识别：

- 场次标题
- 内景/外景
- 地点和时间
- 动作段落
- 人物名和对白
- 括注
- 转场及其他格式标记

无法可靠识别的文本保留为 `unclassified` 来源块并提示人工检查，不允许丢失或直接转成镜头。

### 5.2 场内语义节拍提取

模型调用的最小上下文是完整 Scene，而不是单行文本。模型分析目标、阻碍、行动、反应、揭示、情绪变化、权力变化、转折和结果，并返回严格结构化结果。

模型输出中的每个事实必须引用本 Scene 内的来源范围。模型不能修改或补写对白，也不能引用其他 Scene 的范围。

### 5.3 证据验证

验证器至少检查：

- 来源范围存在且属于目标 Scene
- 人物和对白能在来源中找到依据
- 节拍顺序与原文顺序一致
- 不重复消费或跨越硬场次边界
- 行动、转折和结果具有可核验依据
- `script_fact` 不包含无证据的导演解释

验证失败只阻断对应 Scene 的镜头设计。系统不得退回逐行模式。用户可以修改、重试或人工确认来源映射。

### 5.4 导演与镜头规划

导演规划器接收已经验证的 DramaticBeat、项目风格快照、相关剧本圣经和可用视觉资产。它先输出 DirectorShotIntent，再输出 ShotPlan 和 NarrativeGroupPlan。

场次解析失败、节拍验证失败或关键证据缺失时，下游生成保持不可执行状态。

## 6. 存储、版本与失效传播

`EpisodeSourceStore` 继续作为原始剧本、集文本和来源版本的唯一事实源。新增 `ScreenplaySemanticStore` 只保存按来源版本派生的 Scene、DramaticBeat、验证结果和稳定证据映射。`DirectorPlanStore` 继续保存导演方案，并增加语义版本引用。

所有派生对象记录：

- `source_revision`
- `source_span`
- `source_hash`
- `semantic_revision_id`
- `stale` 状态和原因

失效链为：

```text
ScriptRevision
  -> Scene
  -> DramaticBeat
  -> DirectorShotIntent
  -> ShotPlan
  -> NarrativeGroupPlan
  -> GenerationAttempt / MediaAssetVersion
```

剧本修改时按场次哈希和来源范围计算影响，只标记受影响的后代对象。未受影响场次继续复用。任何失效都不会自动提交图片、视频或配音付费任务。

## 7. Higgsfield 制作方法吸收

### 7.1 ProductionRecipe

提供版本化制作配方：

- `consistency_first`
- `balanced`（默认）
- `motion_enhanced`
- `cost_first`

配方描述角色、场景、道具、镜头语法、叙事组、视频策略、参考优先级、质量控制和成本权重，不包含供应商密钥或 RunningHub 节点 ID。

### 7.2 CharacterVisualBible

将剧本事实、角色设计简报和视觉圣经分离。剧本只提供有证据的人物事实，不直接生成 `face_prompt`。

视觉圣经包含身份锚点和状态资源。服装、年龄、伤势、污渍、湿润、伪装、变形等可见变化建立 CharacterState；普通时期标签不自动创建视觉状态。

### 7.3 SceneBase、SceneState 与 SpatialAnchor

基础场景保存稳定空间结构；结构或陈设变化建立 SceneState；纯光照变化默认复用基础场景并 relight。SpatialAnchor 为不同机位提供一致的空间关系。

### 7.4 ReferencePlan

每次执行前建立类型化参考装配：

- style
- character_identity
- character_state
- scene_base
- scene_state
- prop
- previous_shot
- first_frame
- last_frame

参考默认可见、默认启用并可逐项取消。超出能力额度时必须显示被排除项、原因和优先级，禁止静默截断。

### 7.5 候选版本与采用策略

`GenerationAttempt` 记录实际请求、路由、参考、提示词、参数、供应商任务 ID、费用、错误和输出。`MediaAssetVersion` 表示候选结果，`AssetSlot` 表示当前采用版本。

空槽位的首个 QC 通过结果可以自动标记为暂用；已有当前版本后，新结果只能进入候选区，必须人工替换。失败尝试不得清空已采用素材。

### 7.6 多维 QC

质量检查分为：

- 技术完整性
- 角色、场景、道具和风格一致性
- 叙事与镜头意图正确性
- 人工审美判断

技术硬错误阻断暂用和交付；内容软问题可以保存为候选，并允许用户带理由采用。

### 7.7 视频执行

RunningHub MiniMax H3 继续作为默认核心视频能力。导演层推荐首帧、首尾帧、静帧保持或合成方案，用户在提交前可以调整。实际提示词、参考图、工作流版本、模式、时长、画幅和清晰度必须可见并写入 GenerationAttempt。

## 8. 前端设计

### 8.1 剧本校对

- 原文与规范化文本对照
- 修改差异和版本信息
- 场次解析状态
- 无法识别文本提示

### 8.2 导演拆解

- 左侧 Scene 树
- 中央 DramaticBeat 列表
- 右侧原文证据、戏剧字段和验证问题
- 手动拆分、合并、重排、编辑和局部重试

### 8.3 镜头设计

- DramaticBeat 到 ShotPlan 的关系
- 镜头叙事目的
- 景别、机位、构图、运镜、动作、时长和首尾状态
- 叙事组手动拆分、合并、重排
- 角色、场景和道具需求

### 8.4 成片合成与统一检查器

- ReferencePlan 托盘
- 工作流和参数
- 实际图片/视频提示词
- 候选素材和当前采用版本
- QC 报告
- 任务状态与失败诊断
- 严格模式待确认清单

统计统一为原文行数、场次数、戏剧节拍数、镜头数和叙事组数。

## 9. 旧链删除与迁移

必须删除或退役：

- `literal_script_writer` 任务类型和任务中心映射
- `split_literal_source_text` 作为生产入口
- `modeLiteral` 和“一行一个 Beat”文案
- 前端对 `literal_script_writer` 的兼容监听
- 以原文行数作为 Beat 数量或制作进度的逻辑
- 导演规划器直接把每行原文构造成 SourceSpan 的逻辑
- 验证失败后回退逐行 Beat 的任何分支

旧项目不搬动或删除媒体。旧 Beat 和媒体作为历史数据读取，并标记为 `legacy_unbound`。系统可以生成基于来源、人物、场景和动作的绑定建议，但只有人工确认后才能绑定到新 ShotPlan。

## 10. 错误处理与局部恢复

- 文档格式错误：保留原文并给出位置级诊断。
- 场次解析错误：阻断对应场次，允许人工修正。
- 语义提取错误：保存失败报告，局部重试。
- 证据验证错误：禁止进入镜头设计，不回退旧模式。
- 导演规划错误：只重试失败节拍或叙事组。
- 来源版本冲突：拒绝写入过期结果。
- 供应商错误：保留冻结的 GenerationAttempt，按幂等规则查单或恢复。

## 11. 实施批次

1. 语义契约、场次解析和证据模型。
2. 场内 DramaticBeat 提取、验证和局部重试。
3. 接入现有导演计划并删除逐行 Beat 主路径。
4. 前端四阶段工作台和手动编辑。
5. ProductionRecipe、ReferencePlan、视觉圣经、版本采用和多维 QC。
6. 旧资产人工绑定、局部失效传播和严格交付闸门。
7. 自动化验证与最低成本真实链路烟测。

每个批次独立测试、独立提交并可回退。current main 存在其他终端未提交修改，实施时必须建立本任务文件所有权清单，只暂存本任务拥有的精确变更。

## 12. 验收标准

- YAML、标题、版权字段、时长和分隔线不会生成剧情镜头。
- 一个 DramaticBeat 可以跨多行原文。
- 一个 DramaticBeat 可以生成一个或多个镜头。
- 所有人物、事件和对白事实均可回指原文。
- 模型不得新增原文不存在的对白或剧情事实。
- 修改单个 Scene 不会使整集所有素材失效。
- 前端可查看 Scene、DramaticBeat、ShotPlan 与原文证据关系。
- 用户可手动拆分、合并、重排和修改节拍、镜头与叙事组。
- current main 不再包含“一行一个 Beat”主路径和 `literal_script_writer` 产品入口。
- 旧素材仍可查看，但不会自动错误绑定。
- 新叙事组保持 1～4 镜头和一次组合出图。
- 风格、角色、场景、道具及首尾帧参考在提交前可见、可取消。
- 实际图片和视频提示词、工作流版本及参数可以复盘。
- 新候选不会自动覆盖当前满意素材。
- 技术硬错误阻断交付，严格模式下未人工确认不能最终交付。
