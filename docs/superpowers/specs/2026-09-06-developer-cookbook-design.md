# DramaClaw 开发者 Cookbook 设计

## 背景

DramaClaw 已有安装、部署、概念架构和环境变量文档，但开发者在修改具体功能时，仍需自行连接前端页面、API、领域服务、后台任务、模型调用、存储和测试。现有 `docs/zh/technical-design.md` 适合作为系统概览，不适合持续承载每条业务管线的函数级定位信息。

本次新增一个 Wiki 式开发者 Cookbook，优先回答三个连续问题：

1. 我要修改的功能在哪里？
2. 这个功能依赖哪些模型、状态和约束？
3. 请求从界面进入后，经过哪些模块并最终写到哪里？

## 目标读者与成功标准

主要读者是首次接手模块、修复功能或扩展生产能力的开发者。

Cookbook 达到以下标准时，首版可以交付：

- 开发者能从功能名称进入对应专题，而不需要先理解代码目录。
- 每条核心生产管线都能追踪到前端入口、API 路由、服务或工作流、任务 Runner、外部能力、存储落点和状态回传。
- 常见修改场景明确列出影响层和最小验证集合。
- 页面之间有稳定的上游、下游和相关主题链接，允许像 Wiki 一样连续阅读。
- 文档中的代码路径、关键符号和命令能在当前仓库中验证。

## 范围

首版写透核心生产链路：

```text
小说导入
  → 故事与剧集图谱
  → 角色、场景、道具资产
  → 剧本与语义处理
  → 分镜、草图与首帧
  → 配音与音频
  → 视频生成
  → 合成与导出
```

Freezone、导演世界、聊天助手、模型配置、桌面打包等能力在系统地图中保留入口和边界，但不在首版展开为完整专题。现有用户安装、部署和产品使用文档继续留在 `docs/zh/`，Cookbook 只链接，不复制其正文。

## 组织方案

采用「功能地图 + 纵向管线专题 + 横向开发手册」三层结构：

```text
docs/cookbook/
├── README.md
├── start-software.md
├── system-map.md
├── development/
│   ├── trace-a-feature.md
│   ├── add-api-and-task.md
│   ├── storage-and-files.md
│   └── testing-strategy.md
└── pipelines/
    ├── 01-ingest.md
    ├── 02-episode-graph.md
    ├── 03-production-assets.md
    ├── 04-screenplay.md
    ├── 05-storyboard.md
    ├── 06-audio.md
    ├── 07-video.md
    └── 08-compose-export.md
```

`README.md` 是主要入口，按「我要修改什么」导航，同时提供生产顺序和代码层级两个辅助入口。`system-map.md` 解释所有专题共享的进程、端口、任务、数据目录和状态流。`development/` 保存跨功能复用的方法，避免每个专题重复解释任务系统或测试策略。`pipelines/` 以业务功能为单位描述完整纵向调用链。

## Wiki 链接约定

页面使用普通 Markdown 相对链接，保证 GitHub、IDE 和静态文档工具都能打开，不依赖某一种 Wiki 软件的专有语法。

每篇专题顶部包含：

- 所属阶段
- 上游专题
- 下游专题
- 相关横向手册
- 代码核对基线

每篇专题末尾重复提供「继续追踪」入口。共享概念只在一个权威页面解释，其他页面链接过去。例如任务生命周期由 `development/add-api-and-task.md` 维护，各管线专题只描述自己的任务类型和 Runner。

## 管线专题模板

每篇 `pipelines/*.md` 使用相同结构：

1. **功能边界**：该阶段接收什么、产出什么，以及不负责什么。
2. **核心原理**：主要领域模型、状态转换、幂等或一致性约束。
3. **端到端调用链**：从用户操作开始，依次列出前端路由/组件、Query、API、Service/Workflow、TaskBackend、Runner、模型或 FFmpeg、存储和界面刷新。
4. **关键代码索引**：表格列出路径、符号和职责；路径精确到文件，符号精确到函数或类。
5. **数据与产物**：SQLite 表或 Store、JSON 字段、项目文件目录、中间产物和最终产物。
6. **常见修改场景**：列出需求示例、应修改的层、容易漏改的契约。
7. **失败与诊断**：说明输入校验、任务失败、取消、外部供应商失败和残留状态的观察位置。
8. **验证方式**：给出最小后端测试、前端测试、契约测试和必要的人工检查。
9. **继续追踪**：上游、下游和相关专题链接。

调用链优先使用紧凑文本和 Mermaid 时序图。只有当分支或异步状态仅靠文字难以理解时才增加图，避免图与代码长期脱节。

## 系统地图内容

`system-map.md` 只保存跨专题稳定的系统关系：

- React / TanStack Router 前端如何访问 `/api/v1`。
- FastAPI 路由注册和项目上下文解析。
- `TaskBackend`、任务注册表和 Runner 的关系。
- SQLite、`state/`、`output/`、`runtime/` 的边界。
- 模型网关、媒体能力和 FFmpeg 的调用位置。
- SSE 或查询如何把任务状态返回前端任务中心。
- CE 的本地端口适配器边界。
- 暂未展开的 Freezone、导演世界、聊天助手和桌面壳入口。

该页面不重复产品介绍，也不复制部署手册。

## 证据与可维护性

所有专题应从代码反向整理，证据优先级为：

```text
路由/任务注册与实现
  → 数据模型和 Store
  → 前后端契约测试
  → 现有架构文档与 README
```

若文档与代码不一致，以当前代码和测试为依据，并在文档中使用实际名称。每篇专题记录核对时的 Git commit 短哈希。该字段用于提示文档新鲜度，不表示之后每次提交都必须更新；当入口、任务类型、持久化结构或契约变化时才更新对应专题。

为了降低维护成本：

- 不复制大段源码，只记录路径、关键符号和职责。
- 不列出容易变化但不影响定位的完整参数表；参数细节链接到 schema 或 OpenAPI。
- 共用机制集中写在 `development/`，专题只记录差异。
- 文档检查应验证相对链接和反引号中的仓库路径是否存在。

## 与现有文档的关系

- `docs/zh/technical-design.md` 继续作为新开发者的架构概览，并增加 Cookbook 入口。
- `docs/zh/README.md` 在「概念」或新增的「开发」分组中增加 Cookbook 入口。
- `docs/cookbook/start-software.md` 保留为本地开发启动页，但移除与部署手册重复的内容，并加入返回索引的链接。
- `docs/zh/getting-started/` 和 `docs/zh/guides/` 继续负责用户安装、自托管与排错。

## 实施与验证边界

实现阶段按以下顺序进行：

1. 建立 Cookbook 索引、系统地图、固定模板和链接规则。
2. 整理四篇横向开发手册。
3. 逐条核对并编写八篇核心管线专题。
4. 从现有中文文档增加入口并去除明显重复。
5. 检查 Markdown 相对链接、引用的仓库路径、关键符号和示例命令。

首版不引入新的文档站生成器、自动 API Reference 或源码注释提取工具。验证以静态链接/路径检查、代码搜索和抽样执行开发命令为主。

## 非目标

- 不重写面向最终用户的产品手册。
- 不为所有 API 端点生成逐项参考。
- 不在本次修改业务代码或重构现有管线。
- 不承诺首版覆盖所有实验性和企业版能力。
- 不把 Cookbook 绑定到 Obsidian、GitBook 或其他特定平台。
