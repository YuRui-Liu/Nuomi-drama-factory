# MiniMax H3 精选手法卡片设计

日期：2026-09-29。2026-09-30 对照已合并的导演台实现复核；用户已确认继续实现。

## 1. 问题与目标

画布视频导演台已经支持用户逐片段输入描述、选择首尾帧与共享主体参考，再经项目 runtime 改写为 H3 提示词并提交 RunningHub。用户希望借鉴优秀 MiniMax H3 案例，提高画面动作、表演和运镜的可控性，同时让整理出的手法将来可供叙事组或单 Beat 使用。

首期只给**画布导演台**增加精选手法卡片：用户可为每个片段手动选择一张，AI 将其改写为符合当前素材和 H3 模式的提示词。未选卡时保持现有行为。卡片用于表达导演意图，不替代用户的剧情事实、人物、对白、首尾帧或主体参考。

本设计是在[画布视频导演台既有规格](2026-09-26-canvas-video-director-design.md)上的增量。导演台代码已于 2026-09-30 合并到本地开发分支（`84ceddc`）；这不代表已发布上线。既有“优化失败暂停、不回退原文提交、不增加 QC 闸门”的约定继续适用。

## 2. 已确认的产品边界

1. 首批人工精选约 8–12 张常见短剧手法卡，覆盖人物反应、双人调度、道具动作、静镜头、跟拍和揭示性运镜等；小库先验证，再增补。
2. **每个片段最多一张主手法卡，可不选**。选择由用户完成；首版不自动选卡、不提供用户自建卡或案例全文检索。
3. 卡片内容提炼可迁移的动作节奏、表演/运镜要点与适用条件；不复制第三方完整提示词、视频或案例中的人物、场景。每张卡保留来源链接与来源类型。
4. 卡片不改变视频模型路由、主体参考顺序、帧输入、片段顺序、时长或用户对白；H3 官方规则和本项目 wire 编译器仍决定最终格式。
5. 卡片适用性在选择时说明，在提交时由服务端再次检查。改写结果的必要结构校验不是主观 QC；画布节点不添加评分、反复修稿、生成后审批等门禁。
6. 生成快照留存卡片 ID、版本、内容哈希、当次投影的手法指令和优化结果；后续卡片更新不改写历史任务。
7. 用离线、成对的生成样例比较选卡与未选卡的效果；该评测不成为用户生成的运行时阻断步骤。

## 3. 为什么选择卡片，而非导入提示词库

外部案例多数是为特定图像、角色、场景、时长和风格写的完整提示词。直接拼接到画布片段，容易与用户首尾帧、身份参考或项目已有 H3 规则相冲突，也难以解释哪一部分真正改善结果。手法卡只提炼可复用的**导演动作**，由改写器结合当前事实重写。

候选来源从以下仓库人工检索，优先看故事电影和动作类，再按实际短剧需求补足人物表演与静态镜头：

- [BeatAPI/awesome-minimax-h3-prompts](https://github.com/BeatAPI/awesome-minimax-h3-prompts)：案例、分类与作者来源；其许可说明指出第三方提示词与媒体保留原权利。
- [SkyNotSilent/awesome-minimax-h3-cases](https://github.com/SkyNotSilent/awesome-minimax-h3-cases)：案例、公开提示词与教程的检索线索。
- [stimQQ/stunning-minimax-h3-prompts](https://github.com/stimQQ/stunning-minimax-h3-prompts)：区分作者原文与重建提示词；其 MIT 声明不覆盖作者原文。

仓库自述的案例数量不是效果证据，也不是导入配额。首批卡片由维护者逐条核对原帖/仓库标注，记录 `author_original`、`reconstructed` 或 `analysis_only`，并把多库重复索引归并到同一原始来源。链接供追溯，不把作者原文或视频打包进产品。

## 4. 卡片与适用性契约

手法目录由服务端提供一个稳定、只读、可版本化的目录；前端和优化器读取同一份定义，避免前端显示一种限制、后端执行另一种限制。目录数据独立于 H3 Prompt 文本：未来模型可复用手法语义，再由对应适配器投影。

每张卡至少包含：

| 字段 | 作用 |
| --- | --- |
| `id`、`version`、`content_hash`、`status` | 稳定选择、冻结与退役；旧版本可供历史回放 |
| `title`、`summary`、`category` | 用户浏览和理解预计效果 |
| `intent`、`action_beats`、`performance`、`camera`、`ending_composition` | 可迁移的导演手法，不含案例专属角色/场景 |
| `applicability` | 支持的模式、时长区间及首尾帧约束；以实际工作流能力为上界 |
| `avoid` | 常见冲突，例如强制转场、无缘由换机位、在固定尾帧前新增动作 |
| `sources` | 原始链接、作者/维护者署名、来源类型、核对日期与简短提炼依据 |

首批类目及目标手法如下，具体卡片文案须经过来源核对和片段试用后定稿：固定机位人物反应、细微表情推进、双人视线交接、道具交接与落点、侧向跟拍、缓慢推近、主体入画揭示、环境到人物的揭示、受约束的动作高潮、首尾帧连续过渡。类目不是“电影感”等泛化风格标签；每张卡应说明镜头中**什么发生变化、摄影机如何配合、在哪里结束**。

首期适用模式仅取当前 `validate_generation` 可提交的 `i2v`（首帧）、`fl2v`（首尾帧）和 `ref_only`（纯参考图）。参考图与首尾帧混用、纯文字、仅尾帧均不是首期可选模式。时长以服务端对齐后的实际片段秒数判断，前端使用同一对齐规则预览。

选择控件按片段展示卡片标题、效果摘要、适用模式/时长、来源与限制。与当前片段不兼容的卡片保留可见并解释原因，但不可选。用户改变时长、首尾帧或共享参考导致已选卡不兼容时，保留选择并明确提示，禁止提交该快照；不静默删除卡片或修改模式。未选卡始终有效。

## 5. 数据流与模型边界

```text
片段原始描述 + 首尾帧/主体参考 + 用户所选卡片 ID@版本
  → 画布草稿持久化
  → 服务端解析卡片、核对适用性、冻结卡片内容与图片/片段快照
  → H3 适配层将卡片的手法字段投影为本段的导演意图数据
  → 现有结构化 runtime 改写（原始描述与素材事实优先）
  → 现有 H3 wire 编译与必要结构校验
  → 现有 RunningHub 提交、结果与历史
```

卡片通过结构化 `technique` 数据进入**当前片段**的改写输入，不以外部案例正文覆盖系统 Prompt。改写器只吸收与该片段模式、时长、首尾画面相容的手法；相邻片段仍只作为连续性上下文，不能继承本片段卡片。用户原文、锁定对白、片段 ID、帧数、图片顺序及身份事实优先于卡片。卡片建议与这些事实冲突时返回明确的适用性/改写错误，不自造人物、素材或动作来“满足案例”。

现有实现对应的扩展点：`src/novelvideo/freezone/video_director/models.py` 的 `DirectorSegment`/`DirectorDraft`；`service.py` 的冻结、缓存与任务状态；`optimizer.py` 的逐片段结构化输入；`frontend/src/features/canvas/director/DirectorSegmentEditor.tsx` 的片段编辑。首版不改普通 `VideoNode.tsx` 的运镜模板，也不把卡片逻辑埋入 H3 provider transport。将来叙事组与单 Beat 只读取通用目录和手法字段，由各自的输入编译层适配，不能复用画布的草稿或免 QC 执行策略。

草稿复制片段时复制卡片选择并生成新的片段 ID；删除片段随片段删除选择；重排只改变顺序。生成历史保留已冻结的卡片版本、指令、源链接和改写结果，以便回答“用了哪张卡、实际给模型的是什么”。优化缓存键必须纳入卡片版本/内容哈希；卡片或片段改动后不能复用旧结果。

## 6. 失败处理

| 时点 | 行为 |
| --- | --- |
| 目录读取失败 | 显示卡片暂不可用；未选卡片的既有流程仍可使用；不伪造默认选择 |
| 已选卡 ID/版本不可解析或已失效 | 保留草稿中的选择及提示，阻止该快照提交，允许用户换卡或清除卡片 |
| 当前模式/时长与卡片冲突 | 精确指出片段、卡片与冲突字段；不静默改时长、换模式或删卡 |
| runtime 改写失败或结构无法编译 | 现有画布流程暂停在优化阶段并允许重试；不回退原文直送供应商 |
| 提交后卡片目录更新 | 已提交 attempt 继续使用冻结版本；新生成读取新目录版本 |

不对外部仓库做运行时联网请求，避免生成时因案例站不可用而改变结果。用户草稿与 attempt 的既有版本/并发保护继续生效，旧任务不能覆盖较新结果。

## 7. 验收与效果验证

**契约验收**：未选卡生成与既有行为一致；选卡后只有目标片段收到手法数据；复制、删除、重排、刷新能保持正确的卡片绑定；改模式/时长时前后端给出一致的兼容性结果；历史保存卡片 ID、版本、内容哈希与最终 Prompt；卡片更新不改变旧 attempt；runtime 失败不提交供应商。普通 H3、H3 Ref、首尾帧组合按既有工作流能力分别覆盖，不能以单一模式测试代替。

**质量验证**：选取覆盖静镜、人物表演、双人动作、道具、跟拍和首尾帧过渡的固定短剧片段。对每个片段使用相同输入素材、模型、模式、画幅、分辨率与时长，成对比较“未选卡”和“选卡”结果；若供应商支持可控 seed 则固定并记录，否则记录随机性并重复抽样。盲评记录动作可读性、表演/运镜意图达成、身份与首尾帧保持、首次可用率、单次成本和总成本。测试样本、评估标准与原始结果留存，不能只报告平均分或个别优秀视频。评测是离线的，不加入用户生成路径的 QC 闸门。

首批是否扩大目录，以**相对于无卡基线的实际收益和失败类型**决定。若某卡在多种素材上反复制造冲突，可退役该版本并保留历史证据；不能仅凭外部案例数量或展示视频效果宣称本项目质量提高。

## 8. 非目标与后续扩展

首版不做自动推荐、向量检索、批量搬运完整案例、用户上传手法、视频生成后自动评分或反复修稿。未来可以为叙事组、单 Beat 增加同一目录的选择入口或建议入口，但必须另行定义各自的事实优先级、兼容性和质量策略。后续模型通过模型适配器使用手法字段；不把 H3 wire 文本当成通用卡片内容。
