# 分集剧本追加与批量导入设计

## 背景与目标

当前导入链路以项目唯一的 `novel.txt` 为真相源。第一集导入完成后，前端主动隐藏重新上传入口，后端也没有分集来源、冲突预检或增量提交合同，导致用户无法继续导入第二集。

本设计将导入模型改为“分集原文仓库 + 导入事务”，同时支持：

- 已有第一集后追加单集；
- 一次选择多个文件批量追加；
- 检测重复集号，并由用户逐集选择覆盖或跳过；
- 覆盖时重建项目知识图谱，但保留下游资产并标记为待同步；
- 兼容依赖项目级 `novel.txt` 的现有角色、场景和知识运行时链路。

## 范围与非目标

### 本期范围

- `.md`、`.txt`、`.docx` 分集剧本的单集与批量导入；
- 集号识别、手动补充、冲突预检、覆盖与跳过；
- 分集原文、修订号和导入元数据持久化；
- 项目级合成原文及 Cognee 图谱的一致性更新；
- 覆盖后下游资产过期标记；
- 旧项目的无损迁移。

### 非目标

- 自动删除或重做图片、视频等下游资产；
- 对两个剧本版本进行内容合并；
- 在一次提交中允许部分集正式落库、部分集保持旧版本；
- 替换现有章节解析器或知识图谱实现。

## 核心数据模型

项目新增分集原文目录与清单：

```text
episode_sources/
  episode-0001.md
  episode-0002.md
  episode-0003.md

episode_sources.json
```

每个分集条目至少包含：

```json
{
  "episode_number": 2,
  "title": "地下追逐",
  "source_filename": "E02.md",
  "source_path": "episode_sources/episode-0002.md",
  "content_hash": "sha256:...",
  "imported_at": "2026-08-17T12:00:00+08:00",
  "revision": 1,
  "status": "active",
  "downstream_stale": false
}
```

约束如下：

- `episode_number` 在项目内唯一；
- 新增集初始 `revision=1`；
- 覆盖会递增该集 revision；
- 跳过不会改变文件、修订号、图谱或资产状态；
- `novel.txt` 由所有 active 分集按集号确定性合成，不再作为可直接覆盖的来源；
- 分集原文及清单通过临时目录、文件锁和原子替换提交。

## 集号识别规则

每个文件按以下顺序识别：

1. 解析正文中的章节或集标题；
2. 正文无法识别时解析文件名，例如 `第02集.md`、`E02.md`；
3. 仍无法识别时标记为“待补充”，要求用户手动指定；
4. 正文集号和文件名集号不一致时，以正文为准，并在预检结果中显示警告。

同一批文件内部出现重复集号也视为冲突，提交前必须解决。

## 两阶段导入合同

新增统一接口：

```text
POST /api/v1/projects/{project}/episode-imports/preview
POST /api/v1/projects/{project}/episode-imports/commit
GET  /api/v1/projects/{project}/episode-imports
```

### Preview

`preview` 接受一个或多个上传文件，只执行解析和冲突检测，不修改项目。响应包含：

- 有有效期的 `preview_id`；
- 每个文件的内容哈希、识别集号、标题与解析结果；
- 新增、冲突、待补充、无效格式等状态；
- 当前已存在集的 revision，作为乐观并发基线。

### Commit

`commit` 接受 `preview_id`、手动补充的集号及每个冲突项的明确动作：

- `overwrite`：覆盖已有集；
- `skip`：跳过已有集。

未处理的冲突会阻止提交。提交前重新校验：

- preview 是否存在且未过期；
- 上传内容哈希是否一致；
- 冲突集当前 revision 是否仍与预检时一致；
- 同一批次最终集号是否唯一。

任何校验失败都不修改项目，客户端需重新预检。

## 提交流程与图谱一致性

### 仅包含新增集

1. 将新增分集写入候选目录；
2. 生成候选 `episode_sources.json` 和候选 `novel.txt`；
3. 将新增内容增量加入 Cognee 数据集并完成索引；
4. 图谱成功后原子切换分集清单、分集文件和 `novel.txt`；
5. 写入逐集导入结果。

### 包含覆盖集

1. 将覆盖后的全部分集写入候选版本；
2. 按集号生成完整候选 `novel.txt`；
3. 从全部分集原文清理并重建项目 Cognee 图谱；
4. 图谱成功后原子切换正式分集数据和 `novel.txt`；
5. 对覆盖集递增 revision，并标记下游资产过期。

图谱失败时，旧分集原文、旧清单、旧 `novel.txt` 和旧图谱必须继续可用。候选数据可以保留为诊断信息或安全清理，但不能成为正式状态。

正式 commit 是一个项目内容版本事务。解析预检可以逐文件失败，但提交不会产生“清单已更新、图谱仍是旧版本”的半成功状态。

## 下游资产过期语义

覆盖剧本时不删除角色、场景、分镜、图片、视频或配音。对应集写入：

- 新的 `source_revision`；
- `downstream_stale=true`；
- 各阶段最近消费的 source revision。

前端必须区分：

- 尚未生成；
- 已生成且与当前剧本同步；
- 已生成但来源剧本已更新。

用户可按阶段选择重新规划或重新生成。某阶段成功消费最新 revision 后，只清除该阶段的 stale 状态，不自动清除其他阶段。

## 前端交互

导入页始终提供：

- `追加单集`；
- `批量导入`。

已完成第一集后不再锁死上传入口。旧文件卡作为导入记录显示，但“追加新集”与“替换来源文件”是不同动作。

预检表格至少展示：

| 文件 | 识别集号 | 标题 | 状态 | 用户动作 |
|---|---:|---|---|---|
| E02.md | 2 | 爆发之夜 | 新增 | 导入 |
| E03.md | 3 | 地下追逐 | 冲突 | 覆盖 / 跳过 |
| extra.md | — | — | 待补充 | 设置集号 |

交互规则：

- 无冲突文件默认导入；
- 冲突文件必须逐集选择覆盖或跳过；
- 待补充文件必须指定合法且不重复的集号；
- 提交后显示逐集结果；
- 新增成功后立即刷新分集导航；
- 覆盖成功后显示“剧本已更新，部分资产待同步”及查看入口；
- 失败项支持重新预检和重试，不误报为导入成功。

## 旧项目迁移

当项目存在 `novel.txt` 但不存在分集清单时：

1. 使用现有章节检测器解析原文；
2. 可可靠识别多集时生成对应分集候选；
3. 只能识别一集时迁移为第 1 集；
4. 无法可靠识别时展示一次性确认界面，不自动猜测；
5. 用户确认后原子写入分集目录和清单；
6. 迁移不重建图谱，不修改既有资产，也不改变原始 `novel.txt` 内容。

迁移应幂等：刷新或重复执行不会重复创建分集或递增 revision。

## 错误与恢复

API 和任务中心应明确区分：

- 文件格式不支持；
- 文件解析失败；
- 无法识别集号；
- 集号冲突尚未处理；
- 批次内部存在重复集号；
- preview 已过期；
- 预检后的项目 revision 已变化；
- 图谱增量更新失败；
- 图谱重建失败。

错误响应应包含稳定错误码、用户可行动文案及关联文件或集号。任何正式提交失败都不能隐藏旧项目数据或留下“已导入”的假状态。

## 测试与验收

必须覆盖以下合同：

1. 已导入第 1 集后仍能追加第 2 集；
2. 一次选择多个文件可正确识别、排序并导入；
3. 正文集号优先于文件名集号；
4. 无法识别时必须手动指定；
5. 重复集号必须选择覆盖或跳过；
6. 跳过不改变任何项目状态；
7. 覆盖会从全部分集重建图谱；
8. 覆盖保留下游资产并标记为过期；
9. 图谱失败时旧剧本、图谱和资产仍可使用；
10. 旧项目迁移后可以继续追加且不会重复生成已有集；
11. revision 校验阻止旧 preview 覆盖新状态；
12. API、任务中心和刷新后的前端显示一致的逐集结果；
13. 同批重复集号与正文/文件名冲突均给出明确预检结果；
14. 非 editor 用户不能预检或提交；
15. 上传文件名、路径和大小继续遵守现有安全限制。

## 实施边界

建议将实现拆为四个可独立测试的单元：

1. `episode_sources` 领域服务：识别、清单、合成、revision 与原子提交；
2. 两阶段 API 与任务 runner：预检、提交、错误合同和权限；
3. Cognee 协调器：新增集增量更新、覆盖集全量重建及失败回滚；
4. 前端导入工作台：单集/批量入口、预检表、冲突决策与 stale 状态。

现有 `novel.txt` 消费方继续读取兼容产物，不在本期进行无关重构。
