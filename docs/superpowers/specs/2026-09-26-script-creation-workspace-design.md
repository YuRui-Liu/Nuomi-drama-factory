# 项目级剧本创作工作台设计

日期：2026-09-26  
状态：各设计部分已在讨论中确认；本书面规格待用户集中审阅。  
范围：产品与系统设计，不代表功能已实现。

## 1. 目标与已确认决策

让创作者从一个想法开始，在同一工作台中持续阅读、写作、改稿，形成可以交给糯米制作流程的剧本。主要服务连续短剧，兼容单集与短片。

已确认的决策：

1. 原创创作与已有剧本打磨同时支持；本版不新增完整的小说改编流程。
2. 采用项目级独立「剧本创作」入口，与资产和剧集制作衔接。
3. 文档为主、AI 在旁协作：左侧文档目录，中间正文，右侧助手。
4. 简短讨论后先给全剧框架与首集样稿，校准后逐集推进；不默认批量写完整部。
5. 当前范围先生成候选修改，跨文档影响先提示；用户选择关联范围后再生成关联候选。
6. AI 候选需采纳才能写入正文；手工编辑自动保存。
7. 创作草稿与制作采用版分离；明确交接后才更新制作输入。

## 2. 参考来源与适配原则

参考文章：[阿枫科技《LibTV 的 1.5 大版本来了，五个新功能深得我心》](https://mp.weixin.qq.com/s/bqbxYsLOtofCjQ1TOqDhWQ)，2026-09-22；本次已通过浏览器读取正文。文章描述了用题材、受众、背景等可选项启动原创编剧，以及将已有剧本带入专业导演对话进行调整的交互。

用户另补充了角色造型室、导演执导、3D-BOX 与创意片头的信息。这些补充用于梳理后续衔接，不作为本版全部实现范围，也不将其效果和费用视为独立核实的事实。

借鉴原则：选中创作对象，以专业选项或自然语言表达意图，检查候选，再应用到明确范围。逐处采纳、跨集影响审阅和制作版本隔离是本次为糯米确定的设计，不宣称均已由参考文章验证。

## 3. 本版范围

包含：创作设定、全剧框架与首集生成、逐集续写、已有剧本接入、手工编辑、AI 局部与单集改稿、修改对比、关联建议、一致性检查、版本恢复、人物资产关联、制作交接。

不包含：新的可视化捏脸、跨项目角色库、全资产一键换角、自建导演平台、创作方法导入编辑器、3D 场景与运镜预演、片头生成、实时多人协作、默认整部正文批量生成。已有制作能力继续由原入口负责。

原型为流程演示，顶栏的步骤切换仅用于讨论，不是正式导航要求。初版原型尚未完整表达后来确认的可视化设定与全部状态，文字规格优先。

## 4. 信息架构与现有软件衔接

项目级「剧本创作」工作台：

- 左侧：创作简报、人物与世界设定、全剧大纲、分集梗概、各集正文，以及已确认版本入口。
- 中间：当前文档的阅读编辑区、选段操作、候选差异与版本历史。
- 右侧：讨论、当前引用和修改范围、创作要求、检查结果、关联建议。

单集项目保留简报、设定、故事框架和正文，隐藏多集目录及独立分集梗概。无需建立第二套单集编辑系统。

现有单集页面继续承担场次校对与镜头规划，并提供返回对应创作文档的入口。现有项目可将已有剧本作为起始文档接入，保留来源，不因接入而调用原创生成或自动改写；已有制作采用状态不被自动替换。

## 5. 从想法到首集样稿

### 5.1 创作设定

创意输入区配合可选项：题材及融合方向、受众、时代背景、核心看点、集数、单集目标时长。允许自然语言补充与 AI 推荐，不要求填满所有选项。

AI 只追问会影响创作方向的关键缺口；推荐的值需在生成前显示，用户可调整。集数和时长是目标，不能承诺生成文本或最终成片严格达到时长。

### 5.2 草案产出

用户点击「生成框架与首集样稿」后，按依赖顺序生成：人物与世界设定 → 全剧大纲 → 分集梗概 → 首集正文。生成结果成为可编辑的创作草案，不成为制作采用版。

每份已完成文档可以立即查看。显示当前步骤、已完成结果和失败原因；停止或失败保留已完成内容与要求，重试从未完成步骤继续。依赖文档在期间发生变化时，后续任务不得无提示沿用过期版本；需重新基于当前版本生成。

单集项目生成设定、故事框架与完整初稿，省去分集梗概步骤。

### 5.3 样稿校准与逐集续写

用户通过阅读、直接编辑和 AI 改稿校准首集。点击「按此风格继续下一集」表示采用当前已保存样稿作为风格参考；它与「确认本集并交接制作」是独立动作。

续写使用当前设定、全剧与本集目标、前文已发生事件和明确的写作要求，并记录实际引用版本。已有正文的集数不能被续写按钮直接覆盖；需要转入候选改稿或明确创建新候选。

## 6. 正文编辑与 AI 改稿

### 6.1 手工编辑

支持直接编辑、自动保存、保存中/已保存/失败状态。保存失败保留编辑内容，提供重试；存在未保存内容时不能交接制作或声称该内容已进入生成上下文。

### 6.2 修改入口与范围

选中文字后提供「对白更自然」「增强潜台词」「调整冲突」「压缩篇幅」及自定义要求。也能从场或集发起修改。右侧明确显示引用内容与范围：选段、当前场或当前集。

快捷操作以糯米现有的人物动机、关系利益、场景工艺与语言编辑方法组织，不强加固定反转、打脸、金句或悬念配额。需要保留的剧情结果可作为本轮要求展示。

### 6.3 候选与采纳

AI 输出调整理由与候选差异，在正文对应位置提供前后对照。每处支持采纳、放弃、继续调整；多处支持逐条或整批采纳。候选不直接覆盖当前正文。

每个候选绑定生成时的文档版本、修改范围与原文。若用户随后手工编辑了同一范围，标为「原文已变化」，禁止直接覆盖；可重新生成或重新对照后形成基于最新版本的候选。

整批采纳限于同一轮、同一文档中明确展示的候选。若候选相互依赖或范围重叠，合为一个审阅单元；整批预检发现冲突时不部分写入，先引导处理冲突。跨文档不提供隐式的全部应用。

生成失败保留正文、上下文引用与修改要求。继续调整以候选为参考产生新候选，不视为采纳上一版。

### 6.4 版本恢复

手工编辑和采纳的修改均纳入可恢复历史；候选保留其基线与处理状态。恢复历史版本会创建新的当前修订，不能删除后来历史或悄悄改变制作采用版。恢复后按实际差异更新关联提醒。

## 7. 关联影响与一致性检查

### 7.1 关联建议

当前候选涉及人物事实、知情时间、伏笔或后续情节时，展示受影响文档、原文依据、原因与建议。未采纳时标明「若采纳将影响」；采纳后基于实际当前版本更新建议。

用户勾选范围后，才为选中的关联内容生成候选，仍逐文档审阅采纳。未勾选内容只保留提醒，不被自动修改。所有依据关联到具体文档版本与可定位片段；依据过期后需重新检查。

### 7.2 检查当前集

检查人物动机、关系变化、知情顺序、伏笔及前后事实。每条问题包含原文证据、解释、定位入口和改稿操作。允许标记「这是有意安排」并记录原因；该判断仅针对对应内容版本，相关内容变化后可以重新提醒。

检查属于辅助判断，不保证发现所有矛盾，也不把审美建议作为强制门禁。单集模式只做本篇及其设定的一致性检查。

## 8. 人物叙事档案与制作资产

创作人物保存叙事身份、动机、关系、知情状态等，使用稳定标识关联正文和已有角色档案，不能仅按名字自动合并。

已有角色可由用户明确关联；新人物先建立创作档案，进入制作时再创建或关联角色、造型与音色。重名时要求选择关联对象。

修改叙事动机不自动重做角色图；换演员造型不自动改写对白和剧情。影响制作的角色事实变更进入交接差异，由用户选择后续更新范围。继续保持叙事事实与已确认视觉身份的职责分离。

## 9. 剧本确认与制作交接

### 9.1 采用快照

每集区分当前创作草稿与制作采用版。点击「确认本集并交接制作」前展示尚未处理的一致性提醒；可修正或注明原因后继续。未采纳的候选不进入快照。

交接冻结已保存正文、引用设定版本、人物关联和用户确认记录。下游场次校对与镜头规划只消费该快照，不读取随后变化的创作草稿。

### 9.2 新版更新范围

重新交接时展示相对旧采用版的文本差异、受影响场次、对白、角色引用及已关联素材。可确定的影响与 AI 推测的影响分开展示；无法可靠对应的内容显示「需要重新校对」，不宣称不受影响。

用户选定更新范围后，先更新必要的解析和校对，再通过现有入口执行对应生成任务。仅采用文字新版不自动触发付费媒体重生成。

未更新的旧素材继续保留，其来源版本保持可见；受影响但未更新的结果标为需要处理，不能伪装成已经匹配新版。未受影响素材可复用，复用关系要记录。

### 9.3 幂等、运行中任务和失败

同一项目、集、快照和交接动作重复提交，返回已有交接记录与任务，不重复创建剧集或任务。明确重试复用交接记录，仅重试失败步骤。

运行中的旧版任务继续使用原快照；即使在新版交接后完成，其产物也只能归属于旧版，不能自动提升为新版当前结果。

快照保存后下游派发失败时，保留「待重试/失败」交接状态与原因，允许重试，不要求用户重新确认同一内容。旧制作版与媒体不删除。

## 10. 系统职责、数据与接口边界

本节是逻辑契约，不固定新建某个数据库或服务。实现计划先核对现有存储与任务系统，再扩展；避免为同一剧本维护互不关联的平行版本。

| 单元 | 输入与职责 | 输出与依赖 |
|---|---|---|
| 创作文档 | 项目、文档类型、内容和基线版本；保存修订与历史 | 稳定文档标识、不可变修订；依赖现有项目存储 |
| AI 创作与检查 | 明确修订组成的上下文、创作要求、操作范围 | 草案、修改候选、带证据的问题；依赖现有文本任务运行时 |
| 修改审阅 | 候选、当前版本、用户动作；冲突预检与采纳 | 新修订和审阅记录；依赖创作文档，不调用媒体生成 |
| 制作交接 | 已保存修订、设定引用、角色关联、更新范围 | 采用快照、交接记录、现有制作任务引用 |

最小逻辑对象：

- `CreativeDocument` / `DocumentRevision`：项目、类型、集号、稳定标识、内容、父版本及来源。
- `CreationRun`：生成目标、分步骤状态、上下文版本、产出与失败信息。
- `ChangeProposal`：基线版本、定位范围、原文、候选内容、理由、依赖关系和处理状态。
- `ConsistencyIssue`：证据版本与范围、影响解释、待处理/已处理/有意安排状态和原因。
- `ProductionHandoff`：集、快照、设定与人物引用、更新范围、幂等标识、任务与状态。

核心数据流：创意与设定 → 固定上下文的生成任务 → 创作草案 → 手工编辑或候选审阅 → 新修订 → 关联检查 → 用户确认快照 → 现有场次校对 → 镜头规划与后续制作。

当前已查看的衔接点包括：`frontend/src/routes/_app/projects.$project/episodes.$episode/script.lazy.tsx`、`frontend/src/components/episode/screenplay-workbench/screenplay-workbench.tsx`、`src/novelvideo/api/routes/scripts.py`，以及 `nuomi-drama-scripts` 的人物与对白、场景工艺和审稿方法。现有场次校对的「解析已有剧本，不改写剧情」边界继续成立。实现前再次检查工作树，不能依据旧方案假定所有接口已存在。

## 11. 验收场景与测试重点

使用一部三集短剧贯穿验收，另用一篇短片验证简化模式。

| 场景 | 可观察的通过条件 |
|---|---|
| 从想法开始 | 可选设定后得到框架、三集梗概和首集完整样稿；其他集正文没有被默认生成 |
| 单集模式 | 无多集导航与分集梗概，仍能创作、改稿、检查与交接 |
| 样稿校准与续写 | 首集修改后，下一集使用新设定、样稿和前文事实；已有正文不被直接覆盖 |
| 选段改稿 | 能查看理由与差异，未采纳正文不变，采纳仅更新明确范围 |
| 同范围并发编辑 | AI 生成期间手工改原文，旧候选不能覆盖新编辑 |
| 多处候选冲突 | 整批预检失败时无部分写入；相互依赖的修改合并审阅 |
| 跨集影响 | 修改知情时序后，能定位人物设定和后集相关证据；仅选中的内容生成关联候选 |
| 有意安排 | 可以说明原因，检查结果不强制改写正文；证据变化后重新判断 |
| 人物资产关联 | 改动动机不触发换脸；重名不会静默关联错误人物 |
| 中断与重试 | 已完成文档不丢失，不重复覆盖；依赖已变更时先更新上下文 |
| 版本恢复 | 恢复形成新修订，历史保留，制作采用版不变 |
| 初次交接 | 快照能追溯正文与设定版本，进入现有校对流程 |
| 重复交接 | 同一快照不重复创建集或任务；失败可从原交接记录重试 |
| 制作期间改稿 | 正在运行的任务读取原快照，旧产物不会成为新版结果 |
| 新版交接 | 展示差异与影响，按选定范围更新；未更新的受影响媒体有明确状态 |
| 保存失败 | 编辑保留且可重试，无法将未保存文本作为已确认快照交接 |

验证分层：版本、冲突与幂等以服务契约测试为主；生成中断和交接失败覆盖任务集成；正文选区、候选采纳、关联范围选择及单集布局覆盖前端交互；最后执行三集与单集两条端到端路径。测试验证具体行为，不以 AI 自评高分替代人工读样。

自检关注：原创与导入边界、草案与采用版区分、局部与跨文档修改范围、候选冲突、旧任务产物归属、重复交接、单集兼容，以及本版与后续能力的范围划分。
