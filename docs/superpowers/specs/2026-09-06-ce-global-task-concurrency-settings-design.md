# CE 全局任务并发设置设计

## 背景

本地 CE 当前通过环境变量和代码默认值控制任务并发。用户在界面中看到“队列达到上限”时，无法查看或修改四类队列的限制，且“提交准入上限”和“实际执行并发”由不同参数控制，容易产生已经提高并发但任务仍只排队的误解。

## 目标

- 在顶部“设置 → 运行时与媒体”中提供全局“任务并发”设置。
- 同时管理 `default`、`video`、`world`、`ffmpeg` 四类队列。
- 每类只暴露一个并发值，并统一作用于 CE 的项目准入、单用户准入和实际执行线程池。
- 配置持久化到本机 `STATE_DIR/local/settings.db`，对本机所有项目生效。
- 保存后明确要求重启；同一进程内不部分热更新。
- 保留现有环境变量的运维覆盖能力。

## 非目标

- 不修改 EE、多节点或控制平面的资源调度策略。
- 不开放内部等待队列容量，例如 512、128、64。
- 不支持按项目或按用户分别配置。
- 不尝试在线缩容、取消或迁移正在运行的任务。

## 用户界面

在“运行时与媒体”页新增“任务并发”卡片，位于文本任务路由之后、Codex/Ollama 卡片之前。

卡片包含四个整数输入框：

| 界面名称 | 队列键 | 默认值 |
| --- | --- | ---: |
| 默认任务 | `default` | 3 |
| 视频任务 | `video` | 5 |
| 世界构建 | `world` | 1 |
| 音视频合成 | `ffmpeg` | 1 |

每项允许 1–32。输入为空、非整数或越界时禁止保存并给出字段级说明。卡片同时显示当前进程的运行数和启动时上限，例如“当前 2 / 上限 5”。

保存成功后显示：“任务并发配置已保存，重启服务后生效。”保存不会改变当前进程的准入上限或线程池。

当任一现有相关环境变量覆盖某个队列时，该队列输入框只读，并显示“由环境变量管理”。相关变量包括：

- `ST_PROJECT_MAX_ACTIVE_<LANE>_TASKS`
- `ST_PROJECT_MIN_ACTIVE_<LANE>_TASKS`
- `ST_PROJECT_USER_MAX_ACTIVE_<LANE>_TASKS`
- `ST_CE_GLOBAL_MAX_ACTIVE_<LANE>_TASKS`

环境变量可能分别控制不同层级；API 必须返回实际启动值，界面不把不一致的覆盖伪装成单一可编辑值。

## 持久化模型

复用 `settings.db` 的 `runtime_settings` 表，以单个版本化键 `task_concurrency_v1` 保存：

```json
{
  "default": 3,
  "video": 5,
  "world": 1,
  "ffmpeg": 1
}
```

读取损坏或缺字段的配置时逐项回退代码默认值，不阻止 API 启动；写入时要求四项完整且一次事务提交。

配置优先级为：现有环境变量覆盖 > 已保存界面配置 > 代码默认值。环境变量兼容行为保持不变。

## 后端接口

新增 CE 全局接口：

- `GET /api/v1/task-runtime/concurrency`
- `PUT /api/v1/task-runtime/concurrency`

`GET` 返回：

```json
{
  "ok": true,
  "data": {
    "restart_required": false,
    "lanes": {
      "default": {
        "configured": 3,
        "running_limits": {
          "project": 3,
          "user": 3,
          "executor": 3
        },
        "active": 0,
        "managed_by_environment": false
      }
    }
  }
}
```

四个 lane 均返回相同结构。`configured` 是下一次启动使用的已保存值；`running_limits` 分别描述当前进程的项目准入、用户准入和执行器并发，`active` 描述当前执行数。在没有环境变量管理时，只要保存值与当前三个运行值不一致，`restart_required=true`。

`PUT` 请求包含完整的四项整数配置。后端执行 1–32 校验，原子保存并返回与 `GET` 相同的结构。接口仅在 CE 设置页使用；写权限沿用现有全局设置写入规则，认证关闭的本地 CE 可直接保存。

## 运行时生效规则

服务启动后第一次构建本地任务后端时，读取一次持久化配置并冻结为本进程运行值：

- 项目 active admission limit 使用该值。
- 当前用户 active admission limit 使用该值。
- CE 全局 lane executor 的 worker 数使用该值。

保存操作只更新数据库，不清理或替换进程内快照，因此不会出现“准入已提高但执行器未提高”的半生效状态。重启后四层统一采用新值。

现有环境变量仍可覆盖对应层级。只要某 lane 存在相关环境变量，API 就将其标记为环境变量管理，并返回各层实际启动值；界面不允许覆盖该 lane。

## 错误处理

- 校验错误返回 HTTP 422 和稳定错误码 `TASK_CONCURRENCY_INVALID`。
- 非 CE 环境写入返回 HTTP 403 和 `TASK_CONCURRENCY_CE_ONLY`。
- SQLite 写入失败返回 HTTP 503 和 `TASK_CONCURRENCY_SAVE_FAILED`，不改变旧配置。
- 前端保留用户输入并显示后端消息，不用失败响应覆盖表单。

## 测试策略

后端测试覆盖：

- 无保存值时返回四类默认值。
- 四项配置原子保存并可重新读取。
- 缺字段、非整数、0、33 被拒绝。
- 环境变量优先于保存值，且 lane 被标记为只读。
- 保存后当前进程值不变并返回 `restart_required=true`。
- 新建进程快照后，项目准入、用户准入和执行器并发采用同一个值。
- CE 写权限和错误响应契约。

前端测试覆盖：

- 加载并展示四类配置、运行数和运行上限。
- 合法修改可保存并显示重启提示。
- 非法值禁止保存。
- 环境变量管理的 lane 不可编辑。
- 请求失败时保留输入并显示错误。

最终运行后端定向测试、前端设置组件测试、完整前端测试、CE 构建、Ruff 和 `git diff --check`。

## 验收标准

- 用户可以在设置页一次保存四类全局并发值。
- 设置对本机全部项目生效，不写入项目配置或浏览器缓存。
- 保存后当前进程行为不变化，界面明确提示重启。
- 重启后同一 lane 的准入限制和实际执行并发一致。
- 环境变量覆盖不会被界面静默改写。
