# Nuomi 扩展风格发布技能设计

## 背景

Nuomi Drama Factory 的全局只读扩展风格同时受后端目录模型、来源审计、前端生成快照和预览图资产约束。当前新增一个风格需要人工查找契约、同步多个文件、更新固定数量断言并反复确认流程，容易遗漏，也会消耗大量上下文。

本设计把这套能力收敛为仓库内技能 `publishing-nuomi-extension-styles`，放置于 `skills/`。技能负责指导代理完成创意输入收集、两阶段审批、GPT Image 预览生成、确定性写入、验证和精确提交；配套脚本负责可重复的机器校验和三文件发布。

## 目标

- 让未来任意 Nuomi 项目会话能发现并调用统一的扩展风格发布流程。
- 发布前生成只读计划，必须取得用户明确确认后才修改项目。
- 复用项目真实 `ExtensionStyle` 契约，不在技能中维护第二套字段规则。
- 正常发布只改后端目录、前端生成快照、预览 WebP 三个产品文件。
- 自动拒绝重复 ID、剧情内容偏置、未批准来源、非法预览路径和并发目录漂移。
- 将预览统一为适合现有 UI 的 640×360 RGB WebP。
- 通过技能压力测试证明代理会走短路径，不再重新探索大量文件。

## 非目标

- 不在 Python 脚本中调用付费模型或持有图片服务凭据。
- 不允许技能绕过用户确认直接发布。
- 不把单个扩展风格写死进技能。
- 不把扩展风格升级为普通用户可编辑数据；已发布风格仍由全局目录提供并保持只读。
- 不新增正式产品 CLI 子命令或后台管理界面。

## 目录结构

```text
skills/publishing-nuomi-extension-styles/
├── SKILL.md
├── agents/openai.yaml
├── references/release-manifest.md
├── scripts/publish_style.py
└── tests/test_publish_style.py
```

`SKILL.md` 只保留决策流程和强制门禁；字段细节与示例进入 `references/release-manifest.md`；确定性逻辑集中在 `publish_style.py`；脚本行为由独立测试覆盖。

## 输入契约

技能先把创意结果整理成临时 `release.json`。顶层包含：

- `style`：完整的扩展风格对象，字段由项目 `ExtensionStyle` 模型校验。
- `preview_prompt`：交给 GPT Image 的预览图提示词，不进入产品目录。

`style` 必须包含 `drama_ext.*` 命名空间 ID、名称、说明、分类、六个固定提示词片段 `medium`、`rendering`、`lighting`、`color`、`camera`、`constraints`、预览路径，以及通过来源审计的 `source` 信息。预览路径固定为 `/images/extension-styles/<id-suffix-kebab-case>.webp`。

提示词片段描述稳定的视觉语言，不得写入人物身份、具体剧情、固定场景、事件结果或镜头内文字等故事偏置。`preview_prompt` 应展示媒介、造型、光色和悬念氛围，但同样避免复刻特定作品、角色或受保护标识。

## 两阶段发布流程

### 阶段一：Prepare

调用：

```bash
python skills/publishing-nuomi-extension-styles/scripts/publish_style.py \
  prepare --manifest /tmp/release.json --plan /tmp/release-plan.json
```

`prepare` 执行以下工作：

1. 从仓库真实代码加载 `ExtensionStyle`，校验字段、分类、片段键和值。
2. 检查 ID、预览 URL 和已有目录资产是否冲突。
3. 根据 `source_audit.json` 校验来源仓库、批准状态、40 位小写修订号和 `source_ids`。
4. 应用项目现有故事偏置检测，拒绝将剧情内容固化进全局风格。
5. 计算当前后端目录与前端快照原始字节的 SHA256，并确认二者同步。
6. 生成只读发布计划，包含规范化风格对象、预览提示词、两个哈希和三个目标相对路径。

除用户指定的计划文件外，`prepare` 不修改仓库。校验失败使用退出码 `2`，输出简洁、稳定且可操作的错误信息。

技能计算发布计划文件的 SHA256，向用户展示风格摘要、六片段摘要、来源、预览提示词、计划摘要和将被修改的文件，并等待明确批准。

### 阶段二：Generate and Apply

用户批准后，技能使用 Codex 内置 GPT Image 能力生成一张原始预览图。图片生成由技能层执行，Python 脚本不接触模型调用或凭据。

随后调用：

```bash
python skills/publishing-nuomi-extension-styles/scripts/publish_style.py \
  apply --plan /tmp/release-plan.json \
  --approved-plan-sha256 <已展示并批准的摘要> \
  --preview /path/to/generated.png
```

`apply` 执行以下工作：

1. 重新校验计划内容及当前项目契约，并要求计划文件 SHA256 等于用户批准时展示的摘要。
2. 在目录文件锁内比较后端目录与前端快照 SHA256；若任一文件自 `prepare` 后发生变化，以退出码 `3` 拒绝写入并要求重新准备。
3. 在内存中解码预览图，按中心裁切生成 16:9、640×360、RGB、WebP 输出。
4. 在内存中构造新后端目录和前端快照，并再次校验完整目录。
5. 原子写入后端目录、前端快照和预览 WebP。
6. 输出机器可读的发布摘要，供技能继续验证和提交。

后端目录采用保留原文件内容、仅在数组尾部追加规范化对象的渲染方式，避免无意义地重排历史条目。前端快照继续使用项目标准 JSON 格式。

## 一致性与恢复

`apply` 写入前保存三个目标的原始状态，先生成同目录临时文件，再通过原子替换逐个落盘。如果任一步失败，脚本恢复已替换文件；原先不存在的预览文件会被移除。恢复失败必须作为最高优先级错误报告，不能伪装为成功。

计划记录的目标必须是仓库内固定相对路径，脚本拒绝绝对路径、父目录穿越和自定义产品写入位置。项目根目录默认从脚本位置推导，也允许测试通过显式参数指定临时仓库。

脚本不执行 Git 操作。技能负责在运行写操作前读取项目 `AGENTS.md`；若项目要求 Bash 编辑记录钩子，则对计划列出的每个目标严格执行成对的 before/after 记录。技能不得用此脚本覆盖或提交无关工作区改动。

## 发布后验证

技能在 `apply` 后固定执行：

- 发布脚本自身测试。
- 后端扩展风格目录、注册表、服务与 API 测试。
- 前端扩展风格目录测试。
- 前后端目录同步检查。
- 预览资产尺寸、色彩模式、格式和引用完整性检查。
- `git diff --check` 与精确范围 diff 审阅。

只有全部验证通过才能声明发布完成。用户已授权提交时，技能只暂存本次产品文件与必要的技能/测试文件，不包含其他脏改动。

## 一次性测试契约调整

现有测试将当前 19 个风格视为不可删除或静默变更的基线集合，而不是永远固定的完整集合：

- 基线映射继续精确验证当前 ID、名称和分类。
- 新目录可以追加条目，但所有条目仍必须通过 schema、来源、偏置、唯一性和预览引用检查。
- Registry、Service、API 和前端数量断言从实际目录推导。
- 预览完整性测试遍历实际目录，不再硬编码 `19`。

这使未来标准发布无需编辑测试文件，同时仍能阻止既有全局风格被意外删除或篡改。

## 技能验证策略

技能采用红绿测试，而不仅是检查文件存在：

1. 在无技能条件下给独立代理一个限时发布压力场景，记录其文件探索、遗漏风险和是否缺少审批或并发保护。
2. 先为 `publish_style.py` 编写失败测试，再实现最小逻辑；覆盖 prepare 无副作用、apply 三文件一致、重复 ID、来源不匹配、目录漂移、非法图片与写入回滚。
3. 使用 `skill-creator` 的结构校验器检查 frontmatter、名称和资源布局。
4. 向独立代理提供成品技能并重复同一压力场景，确认它选择两阶段流程、调用脚本、等待确认并执行固定验证，而不是重新手工探索契约。

基线与成品压力测试结果写入实现过程记录，不作为运行时技能资源，避免增加未来调用的上下文成本。

## 完成标准

- 技能位于仓库 `skills/publishing-nuomi-extension-styles/` 并能被 Codex 识别。
- `prepare` 和 `apply` 的成功、拒绝与回滚路径均有自动化测试。
- 项目现有 19 个扩展风格仍通过全部契约测试。
- 测试数量断言完成一次性泛化，模拟第 20 个风格时无需修改测试代码。
- 独立代理的成品压力测试遵守审批门禁并走确定性短路径。
- 工作区中的既有无关修改未被覆盖或提交。
